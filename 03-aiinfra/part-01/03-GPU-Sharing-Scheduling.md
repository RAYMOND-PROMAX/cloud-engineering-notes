# 03 · GPU 共享与集群调度

> **本篇目标：**分清 GPU 共享、资源配额、工作负载排队与模型引擎内部调度，理解它们不能互相替代。

## 1. 为什么需要两类调度

**设备分配**：哪些工作负载可以拿到 GPU、何时得到资源、拿到多少资源，由 Kubernetes 及其调度增强组件处理。

**请求执行**：工作负载已经启动后，单个 vLLM 进程如何组织请求、批处理和 KV Cache，由引擎内部 Scheduler 处理。

```text
训练 Job / 推理 Deployment
      ↓ K8s 或批量调度器：节点、配额、队列、优先级
Pod 获得 GPU 资源
      ↓ 应用加载模型并启动推理引擎
vLLM：WAITING → RUNNING → FINISHED
      ↓ 引擎内 token budget / KV Cache 调度
GPU 执行算子
```

因此，“Kubernetes 显示已分配两张卡”不等于“vLLM 没有等待队列”。

## 2. GPU 共享技术的边界

| 策略 | 实现思路 | 显存隔离 | 适用与限制 |
| --- | --- | --- | --- |
| 整卡独占 | 一个工作负载申请完整 GPU | 独占物理资源 | 适合需要稳定资源边界的训练/推理；存在资源碎片可能 |
| Time Slicing | 把物理 GPU 以时间片方式供多个进程使用 | 通常不提供硬件级显存隔离 | 适合低优先级/开发任务；共卡 OOM 与干扰需要额外控制 |
| MPS | 多 CUDA 进程共享 GPU 执行资源 | 不等同于独立显存分区 | 适合特定小任务并发；需考察架构、限制与故障域 |
| MIG | 支持 MIG 的 GPU 切成独立硬件实例 | 硬件分区能力较强 | 取决于设备型号、分区规格与驱动；并非所有 NVIDIA 卡支持 |

**不要把 time-slicing 的“资源副本数”当作真实 GPU 张数。** 当插件对外暴露多个共享实例时，调度容量的数值可能放大，但物理计算资源并未增加。

### 同一张卡的相互干扰

- 显存竞争：工作负载峰值叠加可能产生 OOM。
- 算力竞争：一方长时间执行可能使另一方延迟抖动。
- 故障域：共享方式不同，进程异常、设备错误的波及范围不同。
- 可观测性：需要分辨 GPU 物理指标、容器级指标和任务级指标，不能将它们直接相加。

## 3. 多租户配额与公平性

配额（Quota）解决“最多允许使用多少资源”；公平性（Fairness）解决“多个团队竞争时如何分配可用资源”；优先级（Priority）解决“资源紧张时谁先获得运行机会”。

它们不是一个参数：

- Namespace ResourceQuota：基本额度限制。
- PriorityClass：决定抢占与排序方面的优先级规则。
- Queue / Project / Department：高级调度平台可能提供组织化资源队列和弹性份额。
- 抢占：可能终止、挂起或重排低优先级任务；训练任务必须考虑 Checkpoint 才能把损失控制在可接受范围。

## 4. Gang Scheduling 为什么出现

分布式训练有“要么所有必要 worker 一起得到资源，要么不启动”的需求。若 8 个 worker 中只有 4 个调度成功，这四个可能占住 GPU 但无法完成有效训练。

**Gang Scheduling** 要求一组任务达到最小就绪成员数或资源条件后再整体执行，以减少半启动造成的资源死锁与浪费。Volcano 等调度扩展常用于这类需求，但具体资源预留、排队与抢占行为取决于调度器配置。

## 5. Run:ai、Volcano、Kubernetes 的角色对比

| 层 | 代表组件 | 解决的典型问题 |
| --- | --- | --- |
| Kubernetes 原生调度 | kube-scheduler | 基础资源、约束、优先级、Pod 绑定 |
| AI 批量任务调度 | Volcano 等 | 队列、Gang Scheduling、批作业资源协调 |
| 企业 GPU 调度平台 | Run:ai 等 | 面向组织的配额、公平性、共享、排队和管理体验 |
| 推理引擎调度 | vLLM Scheduler | 同一推理实例里的序列、KV Block 和 token budget |

选型应先确定工作负载：长时在线推理、可中断离线推理、单机训练、分布式训练，其调度目标和中断成本并不相同。

## 6. 如何观察调度

### Kubernetes 侧

- Pending Pod 数量、事件中的调度失败理由；
- 节点 GPU `Allocatable`、已申请量及 GPU 碎片；
- 不同队列排队时长、工作负载的启动等待时长；
- 抢占次数和被影响任务的恢复时间。

### GPU 设备侧

- GPU 利用率、显存容量与使用量、SM/显存带宽利用情况（如环境提供）；
- GPU 健康、温度、功率及设备错误。

### 推理引擎侧

- Waiting/Running 请求数、KV Cache 使用率、调度抢占次数；
- TTFT、TPOT、吞吐和失败率。

**分析时必须对齐三个时间尺度：Pod 等待分钟级、模型加载秒至分钟级、引擎 token 调度毫秒级。**

## 7. 典型错误决策

- GPU 明明没跑满，就无限增加 time-slicing 副本：可能放大显存争用，并不会创造计算资源。
- 为了吞吐把训练和在线服务无隔离地混在同卡：在线尾延迟风险高。
- 用 `PriorityClass` 代替训练 Checkpoint：高优先级并不会自动保护被抢占任务的工作进度。
- 将 MIG 配置写成所有 NVIDIA 卡通用：必须核对支持清单与具体 profile。
