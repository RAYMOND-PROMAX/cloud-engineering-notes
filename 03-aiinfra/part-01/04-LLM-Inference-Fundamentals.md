# 04 · 大模型推理基础

> **本篇目标：**从 token 生成的过程理解推理时延、显存占用与并发之间的关系，为后续学习 vLLM Scheduler 和性能分析建立基础。

## 1. 推理到底在做什么

自回归语言模型在给定上下文之后，反复预测下一个 token，并将生成结果加入上下文，直到满足停止条件。

```text
用户输入 → Tokenization → Prompt Tokens
          ↓
     Prefill（处理已有上下文）
          ↓
   得到首个输出 Token
          ↓
 Decode（逐步生成新 Token）
          ↓
   Streaming / 最终响应
```

“模型参数量”描述权重规模；“上下文长度”描述模型当前需要处理的 token 数；“并发”描述多个请求同时在系统中运行。它们影响显存和计算成本，但不是同一个概念。

## 2. Prefill 与 Decode 的差别

| 阶段 | 主要工作 | 典型资源特征 | 关键体验指标 |
| --- | --- | --- | --- |
| Prefill | 处理输入 token，构造初始 KV Cache | 大批次矩阵运算，受输入长度和算力影响 | TTFT 的主要组成之一 |
| Decode | 基于已有上下文逐步生成后续 token | 每步计算量较小，容易受显存带宽与 KV 读取影响 | TPOT / ITL、输出吞吐 |

Prefill 可能以 Chunked Prefill 分成多次调度；Decode 也会因为批次、缓存容量、其他请求干扰而出现不均匀的生成间隔。

**注意**：计算受限与访存受限是常见趋势，不是每一种模型或硬件下都绝对成立。

## 3. KV Cache 的必要性

Attention 需要使用已有 token 的 Key 和 Value。如果每次生成新 token 都重新计算所有历史 token，会产生大量重复工作。因此推理引擎通常缓存历史 K/V，后续 Decode 可以复用。

对常规 Transformer 模型，可以用一个简化公式理解 KV 大小：

```text
每 token KV 字节 ≈ 2 × 层数 × KV Head 数 × Head Dimension × 每元素字节数
总 KV 大小 ≈ 每 token KV 字节 × 同时驻留的上下文 token 总数
```

这里的 `2` 表示 K 和 V。该公式是用于直觉和粗略容量估算的模型，未计 Block 对齐、共享前缀、分组、量化、张量并行分片及框架运行时细节。**不同模型架构必须读取配置里的 KV Head 等参数，而不能只按参数量推算。**

## 4. 为什么上下文和并发互相竞争

设想 GPU 只有固定的 KV Cache 容量：

- 单请求上下文越长，占用的 KV Token 越多；
- 同时运行的请求越多，总 KV 需求越高；
- 当资源无法容纳更多请求时，新请求可能等待；
- 某些引擎还可能抢占已有序列，通过重算等方式释放容量。

因此，`max_model_len` 不是越长越好，必须根据任务所需上下文长度与服务吞吐之间做取舍。

## 5. 三种常见时间指标

| 指标 | 定义 | 代表什么 |
| --- | --- | --- |
| TTFT | Time To First Token，从一个约定的请求起点到首 token 返回 | 首字等待体验 |
| TPOT | Time Per Output Token，常见口径为首 token 之后平均每个输出 token 的耗时 | 平均生成速度 |
| ITL | Inter-Token Latency，相邻 token 之间的时间间隔 | 流式输出是否断续 |
| E2E Latency | 从请求开始到完成的整体耗时 | 总完成时间 |

在定义一致且输出 token 数大于 1 时，可做近似分解：

```text
E2E ≈ TTFT + (输出 token 数 - 1) × TPOT
```

不同工具可能以不同时间点计量请求到达、网络发送和首次输出；做对比时要固定统计口径，不能混用网关 TTFT 与引擎 TTFT。

## 6. 吞吐与延迟的关系

- **Requests/s（RPS 或 QPS）**：单位时间内处理的请求数，受输入输出长度分布影响很大。
- **Input Tokens/s**：输入 token 的处理速率。
- **Output Tokens/s**：生成 token 的速率。
- **Goodput**：满足规定 SLO 的有效请求或 token 吞吐；这比只追求最高理论吞吐更贴近服务质量。

并发上升通常会提高批处理效率，但超过容量拐点后，Waiting、KV Cache 压力与尾延迟可能急剧上升。**必须把吞吐和延迟放在同一张负载曲线上分析。**

## 7. 容易混淆的三种排队

1. **网关/应用入口排队**：请求还没被推理引擎接收。
2. **推理引擎 WAITING**：被接收了，但尚未得到调度资源。
3. **设备执行等待**：引擎已安排执行，但 GPU 计算、数据传输或通信仍可能延迟。

这三类等待在不同位置产生，可能需要不同工具才能观察到。
