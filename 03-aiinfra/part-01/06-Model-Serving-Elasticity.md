# 06 · 模型服务与弹性

> **本篇目标：**从“单机模型能回答问题”提升到“可被业务稳定调用的模型服务”，理解接入、路由、部署、扩缩容与发布所处的不同层次。

## 1. 模型进程与模型服务的区别

`vllm serve` 能启动一个 HTTP 服务，但面向多个用户的工程系统还需要解决入口、鉴权、容量、流量分配、负载保护和故障恢复。

```text
Client / SDK
    ↓
API Gateway / Ingress（鉴权、限流、超时、请求日志）
    ↓
Service / Router（实例发现、流量分配、健康状态）
    ↓
Inference Replica A / B / ...（vLLM）
    ↓
GPU + Model Weights + KV Cache
    ↓
Streaming Response
```

在实际架构中，这些能力可能由相同组件组合提供，不要求每一层都单独部署一个软件。关键是**责任和故障边界明确**。

## 2. OpenAI-compatible API 是什么

大模型服务常提供与 OpenAI API 兼容的 HTTP 接口，便于客户端使用统一的 SDK/请求格式。兼容性不等于完全一致，具体支持的 endpoint、工具调用、流式数据、参数和错误语义需要根据框架版本核对。

对于服务方，至少要考虑：

- **模型标识与版本**：客户端如何指定模型？升级时别名如何迁移？
- **Sampling 参数**：`temperature`、`top_p`、最大生成 token 等如何设上限？
- **请求约束**：输入长度、并发、超时、重试与连接断开如何处理？
- **SSE Streaming**：流式响应如何穿越网关，是否因代理缓冲导致首字延迟？
- **可追踪性**：请求 ID 与模型实例日志如何关联，但不得暴露敏感 Prompt。

## 3. Kubernetes 上的服务组成

| 资源 | 通常解决的问题 | 特别注意 |
| --- | --- | --- |
| Deployment | 推理副本和滚动管理 | GPU 数量、启动时间、滚动时额外容量 |
| Service | 负载地址和实例发现 | 只选 Ready Endpoint，避免打到未加载模型的副本 |
| Gateway/Ingress | 外部接入、安全策略、路由 | 流式超时、认证、限流与 TLS |
| ConfigMap/Secret | 配置与凭据管理 | 不应把模型仓库 Token 写入明文 Git |
| PVC / 模型缓存卷 | 模型和数据持久存储 | 模型加载速度、并发读、空间容量 |
| HPA/KEDA 等 | 根据度量驱动副本数变化 | 扩副本之前需有真实 GPU 资源及容量余量 |

**Pod Running ≠ 模型 Ready。** 容器启动后仍可能在下载权重、初始化 CUDA、编译算子、分配 KV Cache。探针需要区分存活、就绪和较长的启动阶段。

## 4. 容器生命周期与探针

- **Startup Probe**：用于初始化可能很长的工作负载，避免尚未完成模型加载就被存活探针反复重启。
- **Readiness Probe**：判断是否可以接受新请求，模型尚未准备好时不应被服务发现。
- **Liveness Probe**：判断进程是否卡死、需要重新启动；不宜用短暂的高负载延迟判定进程死亡。

停止/滚动更新时还需要**优雅下线**：先从 Ready Endpoint 里移除实例，减少新的请求进入，并在允许的时间窗口处理已有的流式连接。是否可以把长对话转移到其他实例，取决于应用设计，并非 Kubernetes 默认提供。

## 5. 三种不同的“弹性”

**A. 应用实例扩缩容**：增加或减少 vLLM Pod，作用是扩展副本总能力，但每个副本通常需要模型权重和 GPU 资源。

**B. GPU 供给弹性**：节点池是否有空闲 GPU？若没有，能否增加 GPU 节点，以及多长时间可用？

**C. 引擎内部弹性**：同一 vLLM 副本通过批处理、缓存和调度在有限 GPU 内处理不同并发。

三者的时间尺度不同：引擎可以逐步调度 token；新副本需要模型加载；新 GPU 节点还涉及设备准备和集群加入。

因此：

```text
HPA/KEDA 决定想要几个副本
       ≠
K8s 保证有足够 GPU 可以调度
       ≠
新副本立即完成模型加载并开始接流量
```

## 6. 用什么指标扩缩容

单纯用 GPU 利用率可能不足以反映在线业务的排队体验。候选指标包括：

- Waiting 请求数或 Queue Time；
- TTFT P95/P99、TPOT；
- KV Cache 压力与抢占；
- 活跃请求数、完成请求率、业务负载趋势；
- 模型加载耗时和当前 Ready 副本数。

需要同时考虑冷启动时间、缩容防抖、最小保障容量和每个新增副本的 GPU 成本。在线服务可优先评估预热副本或保留基础容量，而不是只追求“流量为零时资源为零”。

## 7. 路由与缓存局部性

多副本推理服务可以做简单轮询，也可以进一步按实例负载、队列状态、模型能力、前缀缓存局部性等选择目标。

若高度重复的 Prompt 总被路由到不同副本，单副本 Prefix Cache 命中率可能下降；但过强的“粘性”也可能导致部分副本排队过长。路由策略要在**缓存收益与负载均衡**之间取舍。

安全提示：模型实例共享与缓存复用不能绕过鉴权与数据隔离；请求内容和缓存键不应随意进入高基数、可公开的监控标签。

## 8. 发布、回滚与高可用

推荐把模型/运行镜像、启动参数、模型权重版本、路由配置分别纳入版本管理，并让回滚有明确目标。

```text
新模型镜像/权重准备
    → 离线功能检查
    → 压力与资源验证
    → 小流量灰度
    → 指标与业务质量观察
    → 扩大流量或回滚
```

需要关注的验证项：模型能否启动、首 token 速度、吞吐、错误率、资源占用、回答行为是否符合评测基准、回滚是否能恢复旧版本。

多副本不必然等于高可用：若副本落在同一物理节点、使用同一个不可用存储路径或依赖同一单点网关，故障仍可能同时影响所有实例。
