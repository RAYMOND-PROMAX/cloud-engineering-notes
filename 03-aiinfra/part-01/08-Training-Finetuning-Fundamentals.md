# 08 · 大模型训练与微调基础

> **本篇目标：**了解训练与推理的资源模型区别，建立 SFT、LoRA、分布式训练和 Checkpoint 的基础概念。

**资料覆盖提示：**当前上传的文章重点是 GPU 调度、vLLM 在线推理和私有化部署，训练部分主要是简短介绍及调度应用案例。本篇因此是**基础知识导读（待补充专题资料）**，不宣称已根据这些文章验证训练框架或复现实验。

## 1. 推理与训练的不同

推理通常只需要前向计算和一定的 KV Cache，训练还涉及反向传播、梯度及优化器状态，因此显存与计算资源消耗构成明显不同。

| 维度 | 在线推理 | 模型训练 / 微调 |
| --- | --- | --- |
| 核心任务 | 根据上下文生成输出 | 根据损失函数更新可训练参数 |
| 典型计算 | Forward / Prefill / Decode | Forward / Backward / Optimizer Step |
| 显存主体 | 权重、KV Cache、临时激活 | 权重、激活、梯度、优化器状态 |
| 服务要求 | TTFT、TPOT、成功率、尾延迟 | 吞吐、收敛质量、Checkpoint 与可恢复性 |
| 任务特点 | 请求连续到达、实时性较强 | 通常更长时段，可按批次提交和中断恢复 |

训练中显存是否能容纳，不应简单拿“模型权重 × 2 字节”估算。优化器、梯度与激活常常带来显著额外开销。

## 2. 训练数据与基本过程

常见监督微调（SFT）可简化为：

```text
数据集 → 清洗与格式检查 → Tokenization / Packing
             ↓
      训练 Batch / Forward
             ↓
      Loss 计算 / Backward
             ↓
  Gradient Accumulation / Optimizer Step
             ↓
       Checkpoint / Evaluation
```

注意区分以下概念：

- **Batch Size**：一次迭代处理多少样本；常涉及 micro-batch、梯度累积和全局有效 batch。
- **Sequence Length**：训练样本的 token 长度；长序列显著影响激活显存与计算成本。
- **Learning Rate**：控制更新幅度，依优化器、任务和参数规模选择。
- **Epoch / Step**：数据遍历轮次与参数更新步数并非同一单位。
- **Evaluation**：训练损失下降不等于实际任务质量提升；需独立验证集和目标任务评测。

## 3. 全参数训练与参数高效微调

### Full Fine-tuning

更新模型的大量乃至全部参数，表达能力和训练成本取决于任务与模型规模，通常需要较高 GPU 显存和计算资源。

### LoRA（Low-Rank Adaptation）

为部分线性变换引入可训练的低秩增量参数，基础权重通常冻结，从而减少需要更新的参数量和优化器状态开销。

它并不意味着训练“几乎没有显存占用”：前向、反向所需的激活和计算仍然存在。

### QLoRA

结合量化基础权重与 LoRA 等参数高效训练方法，降低基础权重驻留显存。能否在某张卡上运行仍取决于序列长度、micro-batch、具体量化实现与框架。

## 4. 一次训练更新的逻辑

假设采用梯度累积：

```text
Micro-batch 1 → Forward/Backward → 梯度累积
Micro-batch 2 → Forward/Backward → 梯度累积
Micro-batch N → Forward/Backward → 梯度累积
                               ↓
                   Optimizer Step / Zero Grad
```

一个常用近似关系为：

```text
Global Effective Batch Size
= per-device micro-batch × gradient accumulation steps × data parallel workers
```

实际使用中还须核对框架对分布式 world size 和梯度累积的定义。调大有效 Batch 不等于必然提高模型质量。

## 5. DP、TP、PP 与 ZeRO 的基本分工

| 策略 | 主要目的 | 主要代价 / 限制 |
| --- | --- | --- |
| Data Parallel（DP） | 分发不同样本，提高并行训练吞吐 | 梯度同步和多副本存储 |
| Tensor Parallel（TP） | 将单层计算或张量分配到多个设备 | 跨卡频繁通信 |
| Pipeline Parallel（PP） | 将模型不同层安排到不同设备 | Pipeline bubble、负载不均 |
| ZeRO 等状态分片 | 分摊优化器状态、梯度或参数存储 | 更多通信和系统复杂度 |

“增加 GPU 数量”是否加快训练，要看并行策略与通信成本；当通信/数据加载时间占比很高时，扩容收益可能下降。

## 6. Checkpoint 为什么是工程能力

长时间训练可能因节点故障、任务抢占、磁盘耗尽或人工停机中断。Checkpoint 需要保存**足够恢复训练状态**的信息。

常见内容有：模型权重或 Adapter、优化器状态、学习率调度器状态、全局步数，以及需要保持可复现性的随机数状态等。不同框架和保存策略存在差异。

**恢复训练**与**只加载 Adapter 做推理**是两回事：后者可能只需要推理相关的权重，前者还需要训练过程的状态。

训练调度涉及抢占时，需要综合考虑：

- 每隔多久保存一次；
- 保存一次占用多少 I/O 带宽；
- 从最近检查点恢复会丢失多少计算；
- 保存路径是否可靠；
- 是否真的测试过恢复和继续训练。

## 7. 训练系统如何观测

### 基础设施

GPU 利用率、显存、功率、时钟、PCIe/NCCL 传输、CPU 数据准备和磁盘吞吐。

### 训练过程

Loss、学习率、每秒样本数或 token 数、Step Time、数据加载等待、Gradient Norm、Checkpoint 耗时。

### 质量评估

任务评测集表现、回归测试、泛化能力和安全测试。训练速度高但验证质量下降，不能称为优化成功。

**至少要把“系统是否跑得快”与“模型是否学得对”分开评估。**

## 8. 常见风险和误区

1. **训练 OOM**：不一定是“权重太大”，也可能来自序列长度、激活、Micro-batch 或临时缓冲峰值。
2. **GPU 利用率低**：可能是数据加载、CPU 前处理、通信等待或 Checkpoint I/O 的问题。
3. **Loss 下降**：不能单独证明任务价值和模型泛化能力。
4. **保存了 Adapter**：不等于具备可恢复的训练 Checkpoint。
5. **任务支持抢占**：不等于可以无损中断；需要做实际恢复演练。
