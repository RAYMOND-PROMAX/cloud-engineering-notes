# 09 · 安全与可靠性

> **本篇目标：**理解 AI 基础设施需要保护哪些资产、不同隔离层负责什么，以及如何把故障恢复设计为可验证的工程过程。

**资料覆盖提示：**上传文章对权限、容器安全、可观测性和高可用有分散讨论，但没有提供完整的安全架构标准或高可用实验。本篇为通用框架导读，具体方案仍需结合威胁模型、官方文档和实验验证。

## 1. AI Infra 要保护什么

与一般 Web 服务相比，AI Infrastructure 还要保护 GPU 计算资源、模型权重、训练数据、推理输入输出、Prompt/前缀缓存、Adapter 和 Checkpoint。

| 资产 | 典型风险 | 防护方向 |
| --- | --- | --- |
| API 与用户身份 | 未授权调用、滥用、越权 | 身份认证、细粒度授权、限流、审计 |
| 模型权重 / Adapter | 泄露、篡改、供应链风险 | 仓库权限、哈希校验、镜像与模型来源审查 |
| Prompt/响应 | 敏感内容出现在日志、Trace 或监控标签 | 最小化收集、脱敏、访问控制、保留期限 |
| GPU 资源 | 恶意占用、资源耗尽、共卡干扰 | Quota、优先级、隔离策略、预算 |
| KV / Prefix Cache | 跨请求信息暴露、缓存复用边界不清 | 版本修复、租户隔离、缓存配置审查 |
| Checkpoint / 数据集 | 未授权读取、完整性损失、恢复失败 | 存储 ACL、加密、备份与恢复验证 |

安全不是只在网关加一个 Token。它需要覆盖**身份、网络、运行环境、数据和持续运维**。

## 2. 纵深防护的分层模型

```text
身份与接入：API Key / SSO / OAuth 等，限流，租户权限
       ↓
网络：TLS、Ingress / Gateway、NetworkPolicy、内部服务边界
       ↓
Kubernetes：RBAC、Namespace、SecurityContext、Pod 安全策略
       ↓
容器与节点：镜像来源、漏洞修补、最小权限、驱动更新
       ↓
模型与数据：下载校验、模型仓库授权、日志和缓存隔离
       ↓
审计与恢复：安全事件、告警、备份、演练
```

**Namespace 是管理隔离单元，不自动等于 GPU 硬隔离；time-slicing/MPS 也不代表显存或故障域被完全隔离。** 需要按租户可信程度与硬件能力作出选择。

## 3. 模型服务的安全边界

### 接入层

- 在网关做身份验证、请求大小限制、超时与调用频次控制。
- 将内部推理 `/metrics`、管理端口和模型仓库访问限制在授权网络。
- 限制单用户/租户的并发、输入长度和累计 token 消耗，保护 GPU 容量。

### 容器与节点层

- 使用可信镜像、固定可追踪版本，及时处理依赖漏洞。
- 尽量使用最小权限容器，避免不必要的特权模式与宿主机目录挂载。
- 机密信息使用 Secret 或更严格的凭据管理设施，不写入镜像、Dockerfile、明文配置仓库。
- 统一记录 NVIDIA Driver、容器运行时、GPU Operator 与框架版本，升级前确认兼容矩阵。

### 数据与缓存层

- 不默认记录原始 Prompt/Response；确需审计时做好合法性、最小化和脱敏。
- 多租户使用共享 Prefix Cache 时，关注是否存在跨租户缓存复用的安全限制及相关版本安全通告。
- 模型文件、Adapter 与 Checkpoint 的访问边界应按实际所有权定义，不用“所有运维人员都能读”代替最小权限原则。

## 4. 可靠性不是只有多副本

一个推理服务即使有 3 个副本，也可能因共用 GPU 节点、共享存储、同一网关或同一驱动故障而整体不可用。

高可用设计至少需要考虑：

| 层 | 常见故障 | 对应能力 |
| --- | --- | --- |
| GPU / 驱动 | 掉卡、Xid、OOM、驱动不兼容 | 健康检测、节点隔离、替换或恢复路径 |
| 容器 / Pod | 进程退出、模型加载失败、探针误判 | Startup/Readiness/Liveness、重试与回滚 |
| 调度 | 无卡可用、配额不足、污点冲突 | Pending 排查、容量余量、资源规划 |
| 推理引擎 | KV 压力、排队、抢占、尾延迟失控 | 限流、弹性、缓存与调度参数控制 |
| 网关 | 超时、流式中断、鉴权故障 | 超时预算、实例摘除、回滚与日志追踪 |
| 存储 / 模型仓 | 下载失败、权重损坏、数据源不可用 | 校验、缓存、版本管理、备份策略 |

**可用性声明需要真实监控时间窗、故障定义和统计依据。** 本知识库不预设“99.99%”等未经验证的结果。

## 5. 发布与变更控制

安全补丁、GPU Driver 更新、Operator 升级、模型权重替换、vLLM 升级都属于不同故障风险的变更。

建议每次变更明确：

```text
变更目的与范围
   → 版本兼容检查
   → 影响分析（节点、模型、接口、指标）
   → 预发布/预热验证
   → 灰度与实时观测
   → 成功标准 / 回滚触发条件
   → 变更后核对与记录
```

注意模型服务冷启动可能较慢：即使应用有自动重启能力，如果没有额外容量、缓存或可用副本，故障恢复时间仍可能很长。

## 6. 故障处理的最小闭环

**现象 → 范围 → 证据 → 假设 → 处置 → 验证 → 复盘。**

1. 现象：错误率、TTFT、Pod Pending、GPU 掉卡还是模型返回异常？
2. 范围：单用户、单副本、单节点、单模型还是整个入口？
3. 证据：指标、Event、应用日志、设备日志和最近变更记录。
4. 假设：明确哪一种机制可能造成当前现象。
5. 处置：优先可逆操作；避免把“不明原因的重启”当作根因定位。
6. 验证：指标回到基线、请求完成率恢复、风险已消除。
7. 复盘：把触发条件、失效机制、预防措施纳入可复用文档。

示例：若 Pod Pending，应先看调度 Event 和 GPU 账本，而不是直接重启 GPU Driver；若 TTFT 上升而设备健康，应先看引擎 Queue 和 Prefill，而不是立即扩容节点。

## 7. 灾备与恢复应该验证什么

- 配置和版本是否可恢复；
- 模型权重和依赖镜像是否仍可获取；
- 模型加载后健康探针是否正常；
- 原有客户端接口与鉴权是否兼容；
- 恢复过程中已有请求会如何失败或重试；
- Checkpoint 是否真的能恢复训练，而不只是文件存在；
- 是否能按照明确指标计算 RTO/RPO（仅在适用服务上）。

“有备份”不等于“恢复可用”；恢复程序需要定期演练，并记录失败条件。

## 8. 自测问题

- 为什么 Namespace、RBAC、网络隔离与 GPU 硬隔离是四件不同的事？
- 为什么共享 Prefix Cache 的隔离策略需要和租户权限同时设计？
- 为什么在线服务增加副本后仍可能有单点？
- 遇到 GPU OOM 时，哪些恢复动作可能使其他租户进一步受影响？
- 如何证明一次升级和回滚流程是真实有效的？

兼容、具体威胁模型和实验验证，不能直接当作生产级安全设计方案。
