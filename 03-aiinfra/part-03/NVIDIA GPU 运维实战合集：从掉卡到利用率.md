# NVIDIA GPU 运维实战合集：从掉卡到利用率

GPU 不是一块插在机箱里的加速卡。它自带内存、供电、散热、固件和互联，本身就是一台小机器；出问题的时候，现象几乎总在应用层——训练卡住、推理超时、Loss 突然发散——而根因可能在任意一层：HBM 某一行坏了、PCIe 链路降到 x8、风扇转速掉了、驱动和内核头对不上、调度器把 8 卡作业拆到了两台机器上。

这份大纲把 GPU 运维拆成九个域，每个域回答三件事：要看什么、用什么命令看、什么算异常。它不替代厂商文档，作用是在故障现场先定位到层，再决定翻哪一段。

## 一、硬件与形态：先认清手里是什么卡

SXM 是板载模块，靠 NVLink 与 NVSwitch 互联。一台 8 卡机是一个整体：GPU 焊在基板上，中间是 NVSwitch 交换芯片，单卡不能随手拔，换卡要整机下架。PCIe 是插槽卡，可以单独更换，但卡间通信要走 PCIe 交换，PCIe 4.0 x16 单向带宽约 32GB/s，和 NVLink 不在一个量级。

资产台账里这两类必须分开记。SXM 的备件是整机或整板，返修周期以周计；PCIe 卡可以备单卡，但要注意同批次固件一致。混记的结果是坏了才发现没有对应备件。

显存容量卡住的是模型能不能装下，权重、KV Cache、激活值三块要一起算；显存带宽卡住的是吞吐上限。几代卡的公开规格大致是：A100 80GB HBM2e 约 2TB/s，H100 80GB HBM3 约 3.35TB/s，H200 141GB HBM3e 4.8TB/s。运维看到「显存够但很慢」，多半是带宽或通信，不是卡坏了。

多卡效率取决于互联。有 NVLink 的机器，卡间通信不经过 CPU 与 PCIe，all-reduce 的瓶颈在软件与并行策略；没有 NVLink 的机器，跨卡通信走 PCIe，再跨 NUMA 节点延迟更高。同一批 8 卡作业，拓扑不同，训练时间能差出一截。

MIG 把一张卡切成几份。A100 之后支持，最多 7 个实例，按 GPC 切片，每个实例有独立的显存与 SM，部分 L2 与显存带宽仍是共享的。切了之后实例之间不能共享显存，也不能合并使用；适合推理与小任务混部，不适合需要整卡带宽的训练。

```
# 卡型与序列号，进资产台账
nvidia-smi -L
nvidia-smi --query-gpu=name,serial \
  --format=csv,noheader
# 看卡间是 NVLink 还是 PCIe
nvidia-smi topo -m
```

判据：`nvidia-smi -L` 的条数与台账一致；`topo -m` 里 8 卡之间是 NV 开头的连接，不是 SYS（跨 NUMA）。出现 SYS，说明这张卡和它的兄弟不在同一个 NUMA 域，通信会慢。

## 二、软件栈：版本矩阵比命令行更容易出事

四层结构从下往上：内核驱动、CUDA runtime、框架（PyTorch、TensorFlow 等）、容器镜像。兼容关系不是一条直线。容器里带自己的 CUDA runtime，宿主机只要满足最低驱动版本；但 cuDNN、NCCL 与框架之间有更细的绑定，升错一个，报错信息往往指向别处——典型是框架报「找不到某个算子」，实际是 cuDNN 版本不匹配。

驱动与内核的关系靠 DKMS 维持。内核升级后 DKMS 会重新编译驱动模块，编译需要内核头文件；开了 Secure Boot 的机器还要给模块签名，否则加载失败。这三步任一缺失，表现出来都是「nvidia-smi 找不到设备」，看 dmesg 才能看到真相。

持久化模式值得打开。GPU 在默认模式下空闲会卸载驱动状态，下一次调用要重新初始化，延迟在几百毫秒到秒级；对推理服务，这就是一批超时。`nvidia-smi -pm 1` 常驻，代价是空闲功耗略高。

容器侧有两个开关要能答上来：`docker info` 里的 runtime 是不是 nvidia，`nvidia-container-cli -V` 是否与驱动匹配。新版本也可以用 CDI 方式声明设备，GPU Operator 会把这套东西统一部署。

```
# 驱动与运行时版本
nvidia-smi | head -4
nvidia-container-cli -V
```

镜像里再确认框架报告的 CUDA 版本，一条 `python -c "import torch; print(torch.version.cuda)"` 就能看到。

判据：`nvidia-smi` 右上角的 CUDA Version 是驱动支持的上限，不是已安装版本；容器内框架报告的 CUDA 不能高于它。三者对不上时，先怀疑镜像，不要先动驱动。

## 三、调度与分配：为什么 8 卡作业会散到两台机器

K8s 里 GPU 是整数资源，`nvidia.com/gpu` 只接受整数，requests 必须等于 limits，一个 Pod 占一整张卡。device plugin 把节点上的卡上报给调度器，GFD 再补上型号、驱动版本这类标签（如 `nvidia.com/gpu.product`），让调度能按卡型挑节点。MIG 打开后资源名变成 `nvidia.com/mig-1g.10gb` 这类，粒度细了，可选的组合是固定的。

默认打分倾向摊开。LeastAllocated 把 Pod 分散到不同节点，对在线服务是好事，对 MPI 作业是灾难：rank 散到十台机器，通信全走跨机网络。要整机分配，得靠 podAffinity、topologySpreadConstraints，或者批调度器的 binpack 策略——这也是 Volcano、Kueue 这类组件存在的理由之一。

NUMA 与 PCIe 树决定单机内的效率。一张卡到内存、到网卡的距离不同，跨 NUMA 访问延迟更高。K8s 侧要靠 topology manager 与 CPU 绑核配合；HPC 侧则是调度器的基本盘，Slurm 的整机分配天然对齐拓扑，`--gres=gpu:8` 一次拿满。

```
# 节点上 GPU 的可分配与实际分配
kubectl describe node <node> \
  | grep -A5 gpu
# MIG 实例与可切分档位
nvidia-smi mig -lgip
```

判据：`Allocatable` 与 `Allocated` 两个数对得上账；作业启动后，`topo -m` 确认 rank 落在同一台机器的同一 NUMA 域。

## 四、可观测性：没有 DCGM 就没有 GPU 运维

DCGM 是 NVIDIA 官方的诊断与指标组件，dcgm-exporter 把指标转成 Prometheus 格式，Grafana 出面板。容器环境里通常由 GPU Operator 统一部署，不需要逐台装。

必看的指标分三组。运行状态：利用率 `DCGM_FI_DEV_GPU_UTIL`、显存占用 `DCGM_FI_DEV_FB_USED`、SM 频率与显存频率。健康状态：GPU 温度 `DCGM_FI_DEV_GPU_TEMP`、显存温度 `DCGM_FI_DEV_MEMORY_TEMP`、功耗 `DCGM_FI_DEV_POWER_USAGE`、ECC 双比特与单比特计数、退役页 `DCGM_FI_DEV_RETIRED_DBE`。故障与通信：XID 计数 `DCGM_FI_DEV_XID_ERRORS`、NVLink 带宽 `DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTAL`。

告警要分层，不能一律设阈值。XID 非零直接告警，不需要等累计；DBE 大于零进故障流程；退役页接近硬件上限提前排 RMA；温度与功耗看趋势，不看瞬时值——今天的 78 度和三个月前的 71 度，是散热退化的两个证据点。

```
# ECC、温度、功耗、退役页一次看全
nvidia-smi -q -d ECC,TEMPERATURE,POWER
# DCGM 自带诊断，跑一次留档
dcgmi diag -r 2
```

判据：任取一台机器，能从面板回答三个问题——这张卡谁在用、用了多少、有没有坏。

## 五、故障排查：按层收敛

现象分五类：掉卡（命令看不到设备）、卡死（nvidia-smi 命令 hang）、报错（内核日志里的 XID）、降频（性能掉但没报错）、精度异常（ECC 或通信导致）。五类路径不同，混在一起查会浪费一整晚。

取证顺序固定，先留证据再动手。

第一步 `nvidia-smi -q` 留快照，记录温度、功耗、ECC、退役页、XID 计数；第二步 `dmesg -T | grep -i xid` 看内核日志，时间戳对得上业务曲线；第三步跑 DCGM 诊断；第四步才是复位与换卡。顺序反过来，最常见的后果是把现场证据弄丢了。

XID 按四类理解。显存与 ECC 类：双比特错误、页退役失败。链路类：NVLink 错误、掉总线（fallen off the bus）。固件与驱动类：微控制器挂起、GSP 超时。应用类：显存越界、非法指令。常见码值里，48 是双比特 ECC，63 与页退役相关，74 指向 NVLink，79 是掉总线，119 是 GSP 超时，13 与 31 多来自应用。具体含义以官方 XID 表为准，逐条对应处置，不要凭印象。

掉卡的处理有梯度。先看 `lspci` 里设备还在不在；再看 dmesg 是否报链路错误；然后确认能否软复位；再换槽位验证；最后换卡。GPU 复位会影响同机其他卡，必须确认没有别的作业在跑，不要在业务高峰做。

ECC 与页退役是慢性病。单比特错误会被纠正，但计数累积到阈值会触发页退役；双比特错误通常直接让这张卡不可用。退役页接近硬件上限时，性能与稳定性都会掉，这时候才申请 RMA 已经偏晚。

降频有三种原因：温度墙、功耗墙、时钟被锁。看 GPU 温度与功耗是否顶到上限，再看 `nvidia-smi -q -d CLOCK` 里的时钟是否被限制。机房里夏天一批卡同时降频，通常是进风温度的问题，不是卡的问题。

```
# 内核日志里找 XID，带时间戳
dmesg -T | grep -i xid
# 页退役情况
nvidia-smi -q -d PAGE_RETIREMENT
```

判据：同一 XID 在同一张卡上重复出现两次以上，停止观察，直接进更换流程。观察窗口拉得越长，损失越大。

## 六、性能：利用率低不等于卡坏了

三种低利用率要分开。应用没喂饱（数据管道慢、CPU 预处理跟不上）、模型不适配（batch 太小、并行策略不对）、调度浪费（卡被占着但没跑任务）。前两种是工程问题，第三种是管理问题。

定位靠两条曲线。SM 利用率与显存带宽利用率同时看：都低，瓶颈在卡外；SM 高带宽低，计算密集但访存不友好；SM 低带宽高，在搬数据不在算。再往下看 CPU、网络与存储。

手段按代价排序。调 batch 与并行策略最便宜；开 MPS 让多进程共享一张卡的上下文，次之；MIG 切分只在推理与小任务上划算；换卡换机型是最后一步。

多卡作业还要看通信。NCCL 会打印拓扑检测结果，TP（张量并行）吃卡内带宽、PP（流水并行）吃卡间带宽、DP（数据并行）吃网络。8 卡机内走 NVLink，跨机走 RDMA，两者混在一起时，先确认 rank 的落点，再谈调参。

```
# 进程级占用：谁在吃卡
nvidia-smi pmon -c 1
```

判据：单卡 SM 利用率长期低于 30%、显存带宽也低，先查数据管道与 CPU 亲和，不要先换卡。

## 七、寿命与巡检：坏得最慢的一层最容易漏

温度与灰尘是慢变量。进风口滤网、风扇转速、HBM 温度三条曲线，任何一条在三个月里持续上移，都是散热退化的信号。机房里最贵的故障不是掉卡，是夏天一批卡同时降频。

供电与线缆同样会伪装成 GPU 故障。8 卡机的瞬时功耗很高，PDU 负载不均、供电线缆老化，表现都是「随机掉卡」。巡检要看 PDU 每路负载，而不是只看整机功耗。

固件与驱动要一致。同型号的卡固件版本不统一，同一作业在不同机器上表现会不同，排查时会被误判成应用问题。升级要停机窗口，不要在业务高峰做。

巡检清单固定成六项：温度曲线、风扇转速、ECC 计数、退役页、XID 历史、驱动与固件版本。一个月一次，输出每卡健康分，把 TOP5 风险卡单列出来。

判据：巡检报告能列出 TOP5 风险卡，每张都有处置建议与期限；备件数量能覆盖一个月的返修周期。

## 八、成本与容量：卡买回来只是开始

三层账。账单层是采购与租赁，分摊层按团队与项目拆，单位成本层到每千 token、每训练小时。前两层靠标签，第三层靠作业级记账；没有第三层，容量决策只能拍脑袋。

浪费有三种形态。碎片：一台 8 卡机只用了 3 张，剩下的谁也排不进来。超配：推理副本按峰值配，夜里空转。闲置：卡被占着但进程在等数据。

手段按顺序来：先消碎片，再谈单价。MIG 混部解决小任务占整卡的问题，批处理挪到夜间提高错峰利用率，训练用抢占式节点降单价，推理用弹性节点压空闲。顺序反过来，往往是在错误的规格上买折扣。

判据：GPU 池的平均利用率、排队时长、单卡月成本，三个数能同时给出，容量决策才有依据。

## 九、变更与规范：把上面八条固化

四类变更：驱动、固件、内核、GPU Operator。每一类都要有窗口、验证项与回滚包。回滚不是重装一遍，是提前准备好的旧版本与降级命令，能在半小时内退回去。

演练四种场景：拔卡、掉卡、节点失联、驱动回滚，半年一次。没演练过的应急预案等于没有，真出事时每多问一句就多停十分钟。

文档四份：资产台账（卡型、序列号、位置、保修）、拓扑图、告警说明、RMA 流程，要能在一小时内找齐。

判据：任意一次驱动升级，能在 30 分钟内回滚到上一版，并且作业能恢复。

## 附：十个高频坑

一条一句，都是现场踩过的形状。

一，`requests` 与 `limits` 写成不同值。GPU 是扩展资源，K8s 要求两者相等，写成不同值 Pod 直接起不来，报错还不在 GPU 上。

二，开了 MIG 但 device plugin 没开 MIG 策略。卡仍然按整卡上报，切好的实例没人用得上。

三，容器里看不到卡。宿主机有卡、`nvidia-smi` 正常，容器 `ls /dev/nvidia*` 为空，先查 runtime 与 CDI 声明，不要怀疑硬件。

四，内核升级后 DKMS 没编译。Secure Boot 打开时模块还要签名，症状都是「找不到设备」。

五，没开持久化模式。空闲后第一个推理请求超时，监控上表现为周期性毛刺。

六，8 卡作业散到多台机器。默认打分倾向摊开，MPI 作业要么加亲和，要么用批调度器。

七，温度只看瞬时值。散热退化是三个月的趋势，面板要给的是曲线不是当前读数。

八，ECC 单比特当没事。计数会累积到触发页退役，等到性能掉了再查就晚了。

九，复位前不确认同机作业。GPU 复位影响整机，别人的训练会一起断。

十，用 CPU 指标给 GPU 告警。CPU 不忙的时候 GPU 可能已经贴着温度墙，阈值设错了永远不触发。

判决顺序也简单：前六条是配置问题，看一眼就知道；后四条是流程问题，要靠巡检和变更规范兜住。

九个域里，先做第四（可观测性），再做第五（故障排查），其余按需推进。理由很直接：看不见的层，永远修不好；而 GPU 的故障，八成在看见之前就已经发生过一次。
