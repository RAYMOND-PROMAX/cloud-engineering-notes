# 智能化运维系列03——智能运维数据平台设计：从多源接入到统一数据治理与服务

## 智能运维数据平台设计：从多源接入到统一数据治理与服务

> 第 01 篇建立智能运维知识体系全景，第 02 篇展开可观测性数据的采集与关联，本篇解决多源运维数据如何汇聚、治理、存储、计算和服务化的问题。
> 统一数据平台不是把所有数据强行放进一个数据库，而是建立统一的数据接入规范、数据模型、元数据管理、关联标识、计算处理和数据服务体系。不同类型的数据应根据访问模式、时效要求、保留周期和成本选择合适的存储介质——**数据集中治理，存储按需分布；标准统一，技术异构；服务统一，权限分级**。

## 破题：数据都在，为什么还是拼不出故障全貌

一个中心已经建了 CMDB、Prometheus、集中日志平台、统一告警、ITSM 工单和自动化平台——每个系统都能干活，但一次故障来了，值班人员还是要开六个页面手工拼信息：指标在监控里、日志在日志平台里、变更记录在 ITSM 里、资源关系在 CMDB 里，而"这次异常到底影响了哪个业务"没人能一句话答上来。

问题不在于数据不够，而在于数据散落在不同系统、说着不同的"语言"：同一个 CPU 使用率，A 系统叫 `cpu_usage`，B 系统叫 `cpu.percent`，一个报百分比、一个报字节数。没有统一的标识、模型和关联，数据再多也拼不出完整的故障上下文。

这篇文章讨论智能运维数据平台的完整设计：从多源数据接入、统一数据模型，到分层存储、实时与离线计算、数据治理、统一数据服务，以及如何支撑 AIOps、大模型和 Agent。

## 一、为什么需要建设智能运维数据平台

### 1.1 传统运维数据面临的问题

在实际运维平台建设中，数据通常分散在多个独立系统：

| 数据来源 | 主要数据 | 常见问题 |
| --- | --- | --- |
| 监控系统 | CPU、内存、磁盘、接口指标 | 指标口径不一致 |
| 日志平台 | 应用日志、系统日志、审计日志 | 格式不统一、检索困难 |
| 链路平台 | Trace、Span、服务调用关系 | 无法关联资源和业务 |
| CMDB | 资源、配置项、拓扑关系 | 与实际运行状态不同步 |
| ITSM | 事件、故障、工单、变更 | 缺少运行数据上下文 |
| 自动化平台 | 任务、脚本、执行记录 | 执行结果无法与故障关联 |
| 业务系统 | 交易量、成功率、业务流程 | 业务数据与技术指标割裂 |

这些数据各自能支撑局部运维工作，但没有统一治理和关联机制，就很难回答：某个业务系统当前是否正常？一次接口异常涉及哪些应用、服务器和数据库？故障前是否有变更或发布？某类故障过去发生过多少次、通常怎么解决？某个自动化操作是否真的解决了故障？能否把历史数据用于智能诊断？

### 1.2 智能运维数据平台的定位

智能运维数据平台是连接运维资源、运行状态、运维活动和智能分析能力的基础设施，承担六项核心职责：

1. **统一接入**：接入不同运维系统和基础设施的数据。

2. **统一标准**：建立数据规范、资源标识和指标口径。

3. **统一治理**：完成清洗、校验、补全、去重、质量检查。

4. **统一存储**：按数据类型和使用场景选择存储系统。

5. **统一计算**：支持实时处理、流式计算、离线分析和关联计算。

6. **统一服务**：向监控、告警、故障诊断、知识库和 Agent 提供数据服务。

整套架构自下而上分为六层：运维数据源 → 数据接入层 → 数据存储层 → 数据处理层 → 数据服务层 → 运维应用层，统一标准、资源标识、数据安全、权限审计、运维治理贯穿各层。

> **小结**：数据集中治理，存储按需分布；标准统一，技术异构；服务统一，权限分级。

## 二、数据平台总体架构：从数据源到数据服务

### 2.1 六层技术架构

建议将智能运维数据平台划分为六层。

| 层级 | 名称 | 主要内容 |
| --- | --- | --- |
| 06 | 数据应用层 | 统一监控、告警分析、故障诊断、AIOps、运维 Agent |
| 05 | 数据服务层 | 指标查询、日志检索、事件查询、拓扑查询、诊断上下文 API |
| 04 | 数据计算层 | 实时计算、窗口聚合、离线计算、关联分析、特征加工 |
| 03 | 数据存储层 | 时序数据库、日志检索、关系数据库、消息队列、对象存储 |
| 02 | 数据治理层 | 标准化、清洗、校验、去重、补全、元数据、质量、血缘 |
| 01 | 数据接入层 | Agent、Exporter、OpenTelemetry、API、消息订阅、CDC |

贯穿各层的统一治理与基础支撑包括：数据标准、资源模型、元数据、权限管理、安全审计、数据质量、生命周期。

> **小结**：六层不是六套独立系统，而是**逻辑分层**。实际部署可由多个产品和服务共同实现，也可在建设初期由现有运维平台的部分模块承担。

### 2.2 数据流转架构

数据源经由 Agent、API、CDC 进入接入与消息总线，再分为实时处理和离线处理两条链路：实时处理产出实时数据集市，离线处理汇入历史数据仓库，两者共同支撑统一数据服务，最终被监控告警、智能诊断和 Agent 消费。

这个架构的关键是**数据生产者和数据消费者解耦**：

• 采集系统只负责可靠地生产数据；

• 消息总线负责缓冲、分发和一定时间范围内的数据保留；

• 计算层负责处理、关联和聚合；

• 存储层根据数据类型提供持久化能力；

• 数据服务层屏蔽底层存储差异。

因此，后续增加智能诊断、报表分析、知识检索等新应用时，不必让每个应用都直接对接所有原始系统。

## 三、多源运维数据接入设计

### 3.1 数据源分类

运维数据平台需要接入的不只是监控数据，还应包括资源、流程、配置、操作和业务数据。

| 数据类别 | 数据内容 | 接入方式 | 时效要求 |
| --- | --- | --- | --- |
| 资源数据 | 服务器、数据库、网络设备、应用 | CMDB API、数据库同步 | 分钟级或变更触发 |
| 指标数据 | CPU、内存、连接数、响应时间 | Exporter、OTel、Prometheus | 秒级至分钟级 |
| 日志数据 | 系统日志、应用日志、审计日志 | Agent、OTel、日志接口 | 秒级至分钟级 |
| 链路数据 | Trace、Span、服务调用关系 | OTel SDK、Collector | 秒级至分钟级 |
| 告警事件 | 告警产生、恢复、升级 | 消息订阅、API、Webhook | 秒级 |
| 工单数据 | 事件、故障、变更、处置记录 | ITSM API、CDC | 秒级至分钟级 |
| 自动化数据 | 作业、执行记录、脚本结果 | API、消息订阅 | 秒级至分钟级 |
| 业务数据 | 业务成功率、交易量、处理时长 | API、消息、指标接口 | 依场景而定 |

> **小结**：上述时效是架构设计目标的常见量级，不是所有数据源都能保证的实际 SLA。应结合采集周期、网络、接口限制和系统负载制定接入指标。

### 3.2 接入方式选择

建议根据数据源能力采用多种接入方式，而不是所有数据都通过数据库直连。

| 接入方式 | 适用场景 | 优点 | 风险与边界 |
| --- | --- | --- | --- |
| Agent 采集 | 文件日志、主机状态 | 部署灵活、可持续采集 | 需管理版本和资源消耗 |
| Exporter | 操作系统、数据库、中间件指标 | 生态成熟、指标标准化 | 依赖覆盖范围 |
| OpenTelemetry | 应用指标、日志、链路 | 多语言、多后端 | 需要埋点与上下文传播 |
| REST API | CMDB、ITSM、自动化系统 | 易于集成 | 轮询带来延迟和接口压力 |
| Webhook | 告警、变更、事件通知 | 事件驱动、实时性好 | 需处理重复投递与失败重试 |
| 消息订阅 | 高频事件和异步数据 | 解耦、缓冲、多消费者 | 需管理积压和消费位点 |
| CDC | 业务数据库变更捕获 | 减少全量轮询 | 需评估权限、日志和一致性 |

建议优先级：

1. 有标准消息接口的系统优先使用消息订阅；

2. 有可靠事件回调的系统优先采用 Webhook；

3. 具备标准 API 的系统采用增量 API 同步；

4. 对资源变化不敏感的数据，可采用周期性全量或增量同步；

5. 对必须从数据库同步的数据，优先评估 CDC，**不建议直接对业务数据库进行高频全表扫描**。

### 3.3 统一接入规范

建议每类数据源在接入前形成一份**数据接入契约**，至少包含：数据源名称和责任部门、数据类型和分类级别、接入协议及认证方式、字段定义和样例、资源关联字段、采集周期与最大延迟与数据量估算、重试/幂等/补采/断点续传机制、保存周期和使用权限、验收及异常处理方式。

例如一个数据库监控数据源的接入契约：

source:

name: mysql-monitor

type: metrics

owner: database-ops

protocol: prometheus

collection:

interval: 15s

timeout: 5s

identity:

resource_id: required

instance_id: required

environment_id: required

fields:

- mysql_up

- mysql_global_status_threads_connected

- mysql_global_status_max_used_connections

governance:

classification: internal

retention_days: 90

require_tls: true

```

```

这是便于理解的配置示例，具体字段命名应以所选 Exporter 及平台数据标准为准。

### 3.4 采集数据的可靠性设计

数据采集链路应当考虑以下问题：

• **断网**：Agent 或本地采集端是否具备有限缓存？恢复连接后能否补传？

• **重复**：同一条事件重复投递时，是否通过事件 ID 或业务唯一键实现幂等？

• **乱序**：数据到达时间与事件发生时间不一致时，是否保留两个时间字段？

• **缺失**：采集失败是否产生采集异常事件，而不是把缺失误判为指标为零？

• **补采**：是否支持按资源、时间窗口和数据类型进行补采？

> **小结**：采集失败、数据缺失和真实业务指标为零是三个不同状态，不能混为一谈。

## 四、统一数据模型：解决不同系统的数据语言不一致

### 4.1 为什么需要统一数据模型

不同监控系统可能用不同名称描述同一指标：

| 系统 A | 系统 B | 统一语义 |
| --- | --- | --- |
| cpu_usage | cpu.percent | CPU 使用率 |
| mem_used | memory.used.bytes | 内存已使用量 |
| disk_free | filesystem.free.bytes | 磁盘可用空间 |
| response_time | http.server.duration | HTTP 请求耗时 |
| conn_count | db.connections.active | 数据库活动连接数 |

如果不统一字段定义和单位，跨系统查询和分析就容易出错。例如一个系统的内存使用率单位是百分比，另一个上报的是字节数，直接数值比较显然没有意义。

### 4.2 建议的数据主题模型

可以将智能运维数据划分为以下主题：

| 主题域 | 核心实体 | 典型数据 |
| --- | --- | --- |
| 资源主题 | 资源、配置项、资源关系 | 服务器、数据库、应用、拓扑 |
| 监控主题 | 指标、采集任务、监控规则 | 指标值、阈值、采集状态 |
| 日志主题 | 日志源、日志记录、日志模板 | 日志内容、级别、异常信息 |
| 链路主题 | Trace、Span、服务依赖 | 调用关系、耗时、错误 |
| 事件主题 | 告警、事件、故障 | 异常、恢复、事件状态 |
| 流程主题 | 工单、变更、审批、处置 | 处理过程、审批意见、结果 |
| 自动化主题 | 作业、任务、执行实例 | 执行状态、输出、返回码 |
| 业务主题 | 业务系统、业务指标、业务流程 | 业务量、成功率、交易时长 |

这些主题不是简单的数据库表分类，而是**数据治理、数据服务和权限管理的业务边界**。

### 4.3 建立统一资源标识体系

这是整个数据平台最重要的基础设计之一。建议所有数据都尽可能关联以下标识：

| 标识 | 含义 | 示例 |
| --- | --- | --- |
| tenant_id | 数据所属租户或管理域 | T001 |
| system_id | 业务系统标识 | SYS001 |
| application_id | 应用标识 | APP001 |
| service_id | 微服务标识 | SVC001 |
| resource_id | CMDB 资源唯一 ID | RSC001 |
| instance_id | 运行实例标识 | INS001 |
| environment_id | 环境标识 | PROD |
| event_id | 运维事件标识 | EVT001 |
| trace_id | 分布式调用链标识 | Trace 标识 |

> **小结**：Trace ID 和 Span ID 是链路上下文标识，不能代替 CMDB 资源 ID；IP 地址和主机名是资源属性，不能直接作为稳定主键。

### 4.4 统一数据记录模型

可以设计一个通用的数据元信息结构：

{

"record_id": "REC000001",

"data_type": "metric",

"event_time": "2026-11-20T10:30:00+08:00",

"ingest_time": "2026-11-20T10:30:02+08:00",

"tenant_id": "T001",

"system_id": "SYS001",

"application_id": "APP001",

"service_id": "SVC001",

"resource_id": "RSC001",

"environment_id": "PROD",

"source": "prometheus",

"schema_version": "1.0",

"attributes": {

"metric_name": "cpu_usage",

"value": 85.6,

"unit": "percent"

}

}

```

```

这个模型强调的是**统一元信息和关联字段**，不意味着必须把指标、日志、链路的所有字段塞入一张宽表。不同数据类型仍应使用各自合理的数据结构和存储模型。

### 4.5 时间模型：必须区分事件时间和入库时间

智能运维数据经常存在延迟、补传和乱序，建议至少保留：

• **event_time**：事件实际发生时间；

• **ingest_time**：平台接收数据的时间；

• **process_time**：数据被处理的时间；

• **update_time**：记录最后更新时间。

例如主机在 10:00 发生故障，因网络中断 10:05 才补传。如果仅使用入库时间，就会错误地认为故障发生在 10:05。在后续的实时关联分析中，事件时间窗口、延迟容忍和迟到数据处理都需要基于这一设计。

## 五、数据存储架构：不同数据选择不同存储引擎

### 5.1 为什么不能用一个数据库存储所有数据

运维数据有明显不同的访问模式：指标数据高频写入、按时间范围查询、聚合统计；日志数据大量文本写入、全文检索、条件过滤；链路数据按 Trace ID、服务、时间和耗时查询；资源数据结构化关系查询、事务更新；事件数据状态更新、关联查询、流程管理；历史分析数据大规模扫描、聚合分析、长期留存。

读写模式不同，单一数据库难以兼顾成本、性能和管理复杂度，因此建议采用**多存储引擎架构**。

### 5.2 存储组件选型

| 组件 | 定位 | 边界 |
| --- | --- | --- |
| Prometheus / VictoriaMetrics | CPU、内存、请求量、响应时间等时序数据 | 高基数、高写入和长期留存需单独规划；不应作通用分析型数据库 |
| Loki / Elasticsearch | Loki 标签索引元数据+压缩存正文；ES 适合复杂全文检索与聚合 | Trace ID、用户 ID、订单 ID 等高基数字段不宜作普通索引标签 |
| Apache Kafka | 接收告警、变更、工单、执行记录和高频遥测，实现解耦 | 不是最终数据仓库，也不是面向用户的全文检索服务 |
| 对象存储 + Apache Iceberg | 长期历史归档、跨引擎批量分析，支持 Schema/分区演进与快照 | 不是实时监控数据库，不能替代 Prometheus 或日志检索 |
| 关系型数据库 | 数据目录、接入配置、资源映射、规则配置、事件状态、工单关联 | 不建议将海量原始日志和高频时序指标直接存入 |

### 5.3 推荐的分层存储模型

| 分区 | 定位 | 典型数据 | 主要用途 |
| --- | --- | --- | --- |
| 热数据区 | 高频查询、快速响应 | 最近指标、活动告警、近期 Trace | 实时监控和故障定位 |
| 温数据区 | 中期查询、历史趋势 | 历史指标、日志、工单和事件 | 趋势分析、问题复盘 |
| 冷数据区 | 长期归档、低频访问 | 历史日志、审计记录、历史事件 | 合规留存、长期分析 |

例如可将近 7 天作为热数据、8 至 90 天作为温数据、90 天以上转入归档区。但这只是容量规划示例，实际期限必须按业务需要、数据分类分级和制度要求确定。

### 5.4 数据生命周期管理

数据从产生 → 实时接入 → 热数据存储（高频查询/实时告警/故障诊断）→ 温数据存储（趋势分析/历史检索/统计报表）→ 冷数据归档（审计追溯/长期分析）→ 到期清理或依法依规处置。

需要特别注意：审计日志、业务运行日志和普通监控指标的保存要求可能不同，不能简单设置一个统一保留期限。

## 六、数据计算架构：实时计算与离线计算协同

### 6.1 为什么需要实时和离线两套计算能力

| 业务场景 | 时效要求 | 计算方式 |
| --- | --- | --- |
| 主机 CPU 异常检测 | 秒级至分钟级 | 实时计算 |
| 告警聚合 | 秒级至分钟级 | 流式计算 |
| 变更与异常时间关联 | 秒级至分钟级 | 流式关联 |
| 服务运行趋势 | 小时级至天级 | 离线计算 |
| 故障类型统计 | 天级至月级 | 离线分析 |
| 异常检测模型训练 | 小时级至天级 | 批量计算 |

不能为了追求"实时"把所有任务都设计成流式计算，也不能仅依靠定时任务满足需要快速响应的故障处理场景。

### 6.2 流式计算架构

以 Kafka + Flink 为例：监控指标、告警事件、变更事件、工单事件、自动化事件汇入 Kafka，由 Flink 做告警聚合、时间关联、异常统计，结果写入存储并提供数据服务。Flink 支持有状态流处理，可在多个事件之间维护窗口、计数和模式匹配状态，并通过 Checkpoint 保存状态和流位置以便故障恢复。

### 6.3 一个具体场景：变更与告警关联

假设 10:00 数据库配置变更、10:05 连接池指标异常、10:06 订单服务响应升高、10:07 产生连接超时告警，数据平台需要根据资源标识和时间窗口关联这些事件：

```
收到告警事件 → 获取告警资源ID → 查询该资源最近30分钟变更记录 → 查询关联服务与上下游资源 → 关联相同时间窗口内的异常指标 → 生成诊断上下文 → 输出候选原因及证据
```

示例伪代码：

public DiagnosisContext buildContext(AlertEvent alert) {

// 1. 查询告警资源

Resource resource = cmdbService.getResource(alert.getResourceId());

// 2. 查询相关服务和依赖资源

List<Resource> relatedResources =

topologyService.getRelatedResources(resource.getId());

// 3. 查询时间窗口内的变更

List<ChangeEvent> changes = changeService.queryChanges(

relatedResources,

alert.getEventTime().minusMinutes(30),

alert.getEventTime()

);

// 4. 查询关联指标与事件

List<MetricPoint> metrics = metricService.queryAnomalies(

relatedResources,

alert.getEventTime()

);

// 5. 组装诊断上下文

return DiagnosisContext.builder()

.alert(alert)

.resource(resource)

.relatedResources(relatedResources)

.changes(changes)

.metrics(metrics)

.build();

}

```

```

以上代码是应用服务层的设计示例，不代表某个流计算引擎的完整实现。生产环境还应处理分页、超时、数据缺失、权限过滤、缓存和结果版本等问题。

### 6.4 实时计算与离线计算的边界

• **实时链路**：用于告警聚合、事件关联、实时状态计算；

• **离线链路**：用于历史趋势、模型训练、容量分析和复盘；

• **统一数据标准**：实时和离线计算结果必须遵循相同的资源标识与字段语义；

• **结果可追溯**：保留数据来源、计算时间、规则版本和模型版本。

如果实时和离线计算使用两套完全不同的数据模型，就会出现"实时告警判断正常，历史报表统计却不一致"的问题。

### 6.5 是否需要数据湖和湖仓一体

数据湖或湖仓架构适合：保存大量历史遥测数据、对多年故障/事件/变更/工单联合分析、支持模型训练、多计算引擎共享历史数据、历史数据回放和重新计算。

如果目前主要目标是统一监控、告警和故障处置，且数据规模尚不大，可以先采用"消息队列 + 专用数据存储 + 关系库"的架构。

> **小结**：**不要为了"数据平台"这个概念，在建设初期就引入复杂的数据湖、湖仓、分布式计算集群。技术复杂度应由实际数据规模和分析需求驱动。**

## 七、数据治理体系：让数据真正可信、可用、可管理

数据平台最难的往往不是接入，而是长期治理。如果没有治理，可能出现：同一台服务器对应多个资源 ID、同一指标用不同单位、CMDB 显示已下线但监控仍采集、告警已恢复但事件仍显示处理中、智能诊断使用过期拓扑。

因此建议将数据治理作为平台的**核心能力**，而不是项目后期的补充工作。

### 7.1 数据标准管理

| 标准类别 | 管理内容 | 示例 |
| --- | --- | --- |
| 命名标准 | 数据源、指标、字段、事件名称 | system.cpu.utilization |
| 编码标准 | 资源类型、事件级别、状态码 | SERVER、DATABASE |
| 模型标准 | 实体、属性、关系、时间模型 | 资源、服务、事件 |
| 口径标准 | 指标含义、单位、计算方法 | CPU 使用率百分比 |

建议建立统一指标目录：

| 指标编码 | 指标名称 | 数据类型 | 单位 | 采集对象 |
| --- | --- | --- | --- | --- |
| HOST_CPU_USAGE | CPU 使用率 | Gauge | % | 服务器 |
| HOST_MEM_USED | 内存使用量 | Gauge | Byte | 服务器 |
| MYSQL_CONN_ACTIVE | 活跃连接数 | Gauge | 个 | MySQL |
| HTTP_REQ_TOTAL | HTTP 请求总数 | Counter | 次 | 应用服务 |
| HTTP_REQ_DURATION | HTTP 请求耗时 | Histogram | 秒 | 应用服务 |

其中，指标语义和单位必须明确，不能只依赖字段名称猜测。

### 7.2 数据质量管理

| 检查维度 | 检查内容 | 示例 |
| --- | --- | --- |
| 完整性 | 必填字段是否缺失 | resource_id 不能为空 |
| 准确性 | 数据值是否合理 | CPU 使用率在合理范围 |
| 一致性 | 同一资源信息是否冲突 | CMDB 与采集器标识匹配 |
| 唯一性 | 是否存在重复数据 | event_id 重复检查 |
| 时效性 | 数据是否及时到达 | 指标超过采集周期未更新 |
| 有效性 | 数据是否符合格式约束 | 时间戳格式、单位、状态枚举 |

可以设计数据质量评分：

```
Q = w1·C + w2·A + w3·T + w4·U + w5·V 其中 C 完整性、A 准确性、T 时效性、U 唯一性、V 有效性，Σwi = 1
```

例如某类监控数据完整性 95%、准确性 98%、时效性 90%、唯一性 99%、有效性 97%，可按业务重要程度设置权重形成评分。

> **小结**：该公式是一种可选的**管理度量模型**，不是通用行业标准。评分不能掩盖关键字段缺失等严重问题，建议同时设置硬性质量门槛。

### 7.3 元数据管理

元数据是描述数据的数据。至少应管理：数据源元数据（来源系统、责任部门、接入方式）、结构元数据（字段、类型、单位、Schema 版本）、业务元数据（指标含义、适用范围、业务解释）、技术元数据（存储位置、表名、分区、索引）、治理元数据（分类级别、权限、保留期限）、运行元数据（采集频率、延迟、质量、异常）。

例如用户查询"数据库连接数"，系统需要知道对应哪个指标编码、采集对象是什么、用什么单位、从哪个数据源读取、哪些用户有权限、最近一次更新时间——这些都属于元数据管理范围。

### 7.4 数据血缘与影响分析

数据血缘记录数据从产生、处理、存储到消费的流转关系：MySQL Exporter → Prometheus 采集 → 指标标准化任务 → 时序存储 → 统一指标查询服务 → 故障诊断服务 → 运维分析报表。如果标准化任务出问题，就可沿血缘找到受影响的指标、告警和分析服务。

可研究的标准和项目包括 OpenLineage（数据处理作业运行及输入输出关系）、OpenMetadata（元数据目录、质量、血缘、治理）。

> **小结**：需要区分：这些项目主要面向**通用数据平台治理**，并非专门针对运维数据的 CMDB 或 ITSM 系统。运维平台仍需根据资源、告警、工单、变更等业务实体进行扩展。

## 八、统一数据服务：让数据从存储资源转变为平台能力

### 8.1 为什么需要数据服务层

如果监控、诊断、报表、Agent 都直接访问底层数据库，会出现：各应用需了解不同存储查询方式、业务逻辑分散导致口径不一致、权限控制分散难统一审计、数据库结构调整影响多个应用、Agent 可能绕过业务权限直接访问原始数据。因此建议建立统一数据服务层。

### 8.2 数据服务分类

| 服务类型 | 主要功能 | 典型接口 |
| --- | --- | --- |
| 资源数据服务 | 查询资源和关系 | /resources/{id} |
| 指标数据服务 | 查询实时及历史指标 | /metrics/query |
| 日志数据服务 | 按资源、时间和关键词检索 | /logs/search |
| 链路数据服务 | 查询 Trace 及调用关系 | /traces/{traceId} |
| 事件数据服务 | 查询告警和运维事件 | /events/query |
| 变更数据服务 | 查询配置、发布、变更记录 | /changes/query |
| 工单数据服务 | 查询故障及处置记录 | /tickets/query |
| 诊断上下文服务 | 聚合多源数据 | /diagnosis/context |

## 九、数据平台如何支撑 AIOps、大模型与 Agent

数据平台的最终价值，不是把数据存起来，而是让数据能够被算法理解、被业务使用、被智能体安全调用。

### 9.1 为 AIOps 算法提供特征数据

AIOps 算法需要的不只是单个 CPU 指标，还可能需要：同一资源过去一段时间的指标变化、同一服务的请求量和错误率、上下游服务异常状态、相同时间窗口的日志异常数量、资源拓扑和依赖关系、近期变更和工单记录、历史故障类别和处置结果。

例如针对数据库连接数异常，可构造以下特征：

| 特征 | 含义 |
| --- | --- |
| conn_current | 当前连接数 |
| conn_max | 最大连接数 |
| conn_growth_rate | 连接数增长速率 |
| conn_waiting | 等待连接数 |
| query_latency_p95 | 查询 P95 耗时 |
| error_rate | 连接错误率 |
| recent_change | 是否近期发生变更 |
| service_error_rate | 关联服务错误率 |

### 9.2 机器学习与大模型如何协同

| 技术 | 适合承担 | 不适合单独承担 |
| --- | --- | --- |
| 规则引擎 | 明确阈值、确定性条件判断 | 复杂未知异常识别 |
| 统计分析 | 趋势、波动、基线分析 | 复杂语义解释 |
| 机器学习 | 异常检测、模式识别、风险评分 | 自然语言知识解释 |
| 图分析 | 拓扑关系、依赖影响分析 | 非结构化文本理解 |
| 大模型 | 多源信息归纳、解释、生成报告 | 无证据的确定性根因判断 |
| Agent | 按权限调用数据和工具、编排流程 | 绕过审批执行高风险操作 |

推荐流程：多源运维数据 → 统一数据平台 → 规则与算法分析（异常检测、关联分析、候选根因及评分）→ 大模型分析（结合上下文、检索历史知识、生成解释）→ Agent 编排 → 权限校验与人工审批 → 自动化工具执行 → 采集执行结果和恢复指标 → 更新事件及知识记录。

### 9.3 RAG 需要什么样的数据底座

RAG 并不是简单地把所有运维数据向量化，需要区分两类数据：

**适合进入知识库的数据**：运维制度和操作规范、故障案例和复盘报告、标准操作手册、系统架构说明、故障处理流程、常见问题和解决方案。

**更适合通过结构化查询获取的数据**：当前 CPU/内存/磁盘指标、实时告警和事件、当前资源关系、最新变更记录、当前工单状态、实时链路和日志。原因是实时运行状态变化频繁，直接依赖向量检索容易获取过期数据。

建议采用混合架构：故障诊断请求分为结构化数据查询（实时指标/日志/事件）和 RAG 知识检索（历史案例/制度/手册）两路，汇总为证据后交给大模型生成诊断报告。

> **小结**：对于运维知识库，应保留知识来源、版本、更新时间、适用系统、适用环境和访问权限。检索结果必须做权限过滤，**不能让用户通过 RAG 间接获取其无权访问的运维资料**。

### 9.4 MCP 与 Agent 数据访问

可以将数据服务封装为受控工具，通过 MCP（Model Context Protocol）向 Agent 提供标准化访问入口：智能运维 Agent → MCP Client → MCP Server（query_resource、query_metrics、search_logs、query_trace、query_events、query_changes、query_tickets）→ 统一数据服务 → CMDB/监控/日志/ITSM。

关键不是把所有数据库连接直接暴露给模型，而是把经过授权、参数校验和审计的数据服务包装成有限的工具：

• query_metrics 只允许查询授权资源和时间范围；

• search_logs 限制最大返回条数，并对敏感字段脱敏；

• query_changes 只允许读取有权访问的变更记录；

• create_ticket 属于写操作，需要额外权限及必要审批。

> **小结**：MCP 只是工具交互协议，不能替代身份认证、业务授权、审批流程和安全审计。

## 十、实战案例：建设统一运维数据平台，支撑故障诊断

### 10.1 建设目标

某中心已建设 CMDB、Prometheus、集中日志平台、统一告警、ITSM 工单、自动化运维平台，各系统相对独立。目标：统一汇聚多源数据、统一资源 ID 和数据模型、统一关联指标/日志/链路/告警/变更/工单、提供标准查询服务、支撑智能故障诊断和后续 Agent 建设。

### 10.2 建设后的总体架构

数据来源系统（CMDB、Prometheus、日志、链路、ITSM、自动化）→ 统一接入与数据总线（OTel Collector、API 适配器、Webhook、Kafka、CDC）→ 统一数据治理中心（数据标准、资源映射、清洗、质量、元数据、血缘）→ 分类存储（指标、日志、事件流程、历史分析）→ 统一数据服务中心 → 智能运维应用。

### 10.3 核心模块划分

| 模块 | 核心职责 | 主要功能 |
| --- | --- | --- |
| 数据接入管理 | 管理数据源 | 数据源配置、接入任务、采集状态 |
| 数据标准管理 | 维护统一规范 | 指标目录、字段标准、数据字典 |
| 数据治理管理 | 保证数据质量 | 清洗、转换、去重、校验、补全 |
| 资源映射管理 | 建立统一关联 | 外部资源 ID 映射、资源关系同步 |
| 数据存储管理 | 管理数据存储 | 存储配置、生命周期、容量监测 |
| 数据计算管理 | 处理数据 | 实时任务、离线任务、关联计算 |
| 元数据管理 | 管理数据资产 | 数据目录、字段、血缘、责任人 |
| 数据服务管理 | 提供数据能力 | API、查询服务、数据订阅 |
| 数据安全管理 | 控制数据使用 | 分类分级、权限、脱敏、审计 |

> **小结**：数据平台负责数据接入、治理、关联和服务，**不应重复建设 CMDB、ITSM 和监控系统的全部业务功能**。CMDB 仍是资源模型权威系统，ITSM 仍负责工单与变更流程，监控系统仍负责指标采集与规则执行；数据平台负责汇聚这些数据，形成跨系统统一查询与分析能力。

### 10.4 建议的数据库与核心表设计

初期可用关系数据库管理元数据和业务配置：

| 表名 | 主要用途 | 核心字段 |
| --- | --- | --- |
| ods_data_source | 数据源配置 | source_id、source_type、endpoint |
| ods_ingest_task | 接入任务 | task_id、source_id、status |
| meta_data_standard | 数据标准 | standard_id、field_name、data_type |
| meta_metric_catalog | 指标目录 | metric_code、unit、description |
| meta_resource_mapping | 资源映射 | source_resource_id、resource_id |
| meta_data_asset | 数据资产 | asset_id、asset_type、storage_location |
| meta_data_lineage | 数据血缘 | source_asset_id、target_asset_id |
| dwd_event_relation | 事件关联关系 | event_id、related_event_id、relation_type |
| dws_diagnosis_context | 诊断上下文记录 | context_id、event_id、context_version |

需要注意：指标明细和日志明细不建议直接放入上述关系库；表命名只是分层建模示例；数据规模较大时还需考虑分区、索引及归档策略。

## 十一、工程实施路线：如何分阶段建设

**第一阶段：建立数据底座。** 梳理现有系统和数据源；建立统一资源标识和映射；制定指标/日志/事件数据标准；建设接入管理和基础治理；建立统一存储和查询接口；完成 CMDB、监控、告警、ITSM 数据接入。阶段成果：统一接入能力、初步统一数据模型、多源汇聚、统一资源关联、跨系统查询。

**第二阶段：建立数据分析能力。** 建设 Kafka 消息分发；实时事件处理和告警聚合；指标/日志/链路/变更关联；数据质量、元数据和血缘管理；历史数据归档和分析；诊断上下文服务。阶段成果：多源关联分析、统一事件模型、故障上下文自动汇聚、趋势分析和复盘。

**第三阶段：支撑智能运维。** 异常检测和特征数据服务；故障知识库和 RAG 检索；算法分析与诊断服务；诊断上下文封装为 Agent 工具；工具授权、审批、审计和执行验证；根据处置结果持续优化。阶段成果：智能异常检测、多源驱动诊断、大模型辅助分析、受控 Agent 调用。

### 11.1 建议的验收指标

不建议只用"接入了多少系统、建设了多少张表"衡量价值：

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| 接入能力 | 数据源接入覆盖率 | 已接入与计划数据源比例 |
| 数据质量 | 关键字段完整率 | 资源 ID、时间戳等完整程度 |
| 数据质量 | 数据采集成功率 | 成功采集占应采集比例 |
| 数据时效 | 数据处理延迟 | 发生到可查询的时间差 |
| 资源关联 | 资源映射成功率 | 成功关联 CMDB 的比例 |
| 数据治理 | 标准化覆盖率 | 符合统一规范的数据比例 |
| 数据服务 | 查询成功率 / 响应时间 | 按类型统计 P95/P99 |
| 数据分析 | 事件关联率 | 能关联资源和上下文的事件比例 |
| 智能应用 | 诊断上下文完整率 | 诊断所需关键数据可获取程度 |

建议先进行现状测量，再制定目标值。特别是数据关联率和诊断上下文完整率，应根据实际故障类型定义必需字段，不能仅以数据条数衡量。

## 十二、常见建设误区

| 误区 | 实际问题 | 改进建议 |
| --- | --- | --- |
| 把数据平台理解成数据仓库 | 缺实时监测和快速查询 | 实时链路与历史链路协同 |
| 所有数据存一个数据库 | 访问模式不同难兼顾 | 多存储引擎+统一服务屏蔽差异 |
| 只汇聚不治理 | 字段、资源、时间仍不一致 | 同步建资源映射、标准、质量、元数据 |
| 过早引入复杂大数据技术 | 成本与复杂度高 | 按规模与需求逐步演进 |
| 让 Agent 直接访问底层库 | 权限不清、审计困难 | 通过统一数据服务和 MCP 受控访问 |

## 十三、安全与治理要求

智能运维数据平台汇聚大量基础设施、业务系统、日志和操作记录，安全要求必须贯穿数据生命周期。

### 13.1 数据分类分级

建议从普通运行监控数据、内部系统运行日志、业务系统运行数据、运维操作与审计数据、涉及敏感业务或个人信息的数据等维度分类。不同类别设置不同采集范围、存储位置、访问权限和保留策略。具体分级应遵循组织制度和法律法规，**不能简单按照字段名称判断**。

### 13.2 数据访问控制

建议采用 RBAC、用于资源/环境/数据级约束的 ABAC、多租户或多管理域隔离、敏感字段脱敏、API 认证授权、数据导出审批审计、访问行为留痕。

### 13.3 数据接入安全

Agent 和 Collector 使用可信身份接入；系统间通信采用安全传输；密钥、Token 等集中管理；对外部系统接入设置网络边界和白名单；对消息队列设置 Topic 级权限；对采集异常、数据篡改和异常访问进行监测。

### 13.4 数据平台自身的高可用

| 组件 | 高可用设计 |
| --- | --- |
| 数据接入 | 多实例部署、失败重试、有限本地缓存 |
| Kafka | 多 Broker、副本机制、容量监控 |
| 实时计算 | Checkpoint、故障恢复、状态备份 |
| 指标存储 | 按部署模式配置冗余、备份和扩展 |
| 日志存储 | 多节点、存储冗余、索引恢复 |
| 关系数据库 | 主备或集群、定期备份 |
| 数据服务 | 多实例、限流、超时和熔断 |
| 元数据 | 备份、版本管理、变更审计 |

> **小结**：需要特别强调：Kafka 副本机制、Flink Checkpoint 和数据库备份解决的问题并不相同，不能相互替代。数据平台还需要定期开展**恢复演练**，验证数据是否真正能够恢复。

## 十四、核心技术选型建议与适用边界

| 技术层 | 推荐技术 | 主要用途 | 选型边界 |
| --- | --- | --- | --- |
| 数据接入 | OpenTelemetry Collector | 统一遥测数据接入 | 特殊设备仍需专用采集器 |
| 消息总线 | Apache Kafka | 事件缓冲、数据分发 | 小规模可先用现有消息中间件 |
| 实时计算 | Apache Flink | 事件关联、窗口计算 | 简单规则不一定需要独立集群 |
| 指标存储 | Prometheus / VictoriaMetrics | 运行指标存储 | 长期历史分析需扩展 |
| 日志存储 | Loki / Elasticsearch | 日志检索与分析 | 按检索需求和成本选择 |
| 链路存储 | Jaeger / Tempo | Trace 查询 | 与现有后端协同 |
| 关系存储 | PostgreSQL 或适配的国产数据库 | 元数据、配置、事件关系 | 根据目标环境兼容性测试 |
| 历史分析 | 对象存储 + Iceberg | 历史数据分析 | 初期可暂缓 |
| 元数据治理 | OpenMetadata 等 | 数据目录、血缘、质量 | 需适配运维业务模型 |
| 可视化 | Grafana | 多源数据可视化 | 不能替代业务应用和事件中心 |

以上是参考选型，不是要求全部引入。对已有运维平台而言，最优方案通常不是重新采购或部署完整技术栈，而是**优先复用已有组件，通过统一标准、资源映射和数据服务完成能力整合**。尤其在信创环境中，应先做 CPU 架构、操作系统、数据库、中间件和依赖库的兼容性验证。

## 十五、延伸阅读：官方文档与技术资料

| 技术资料 | 建议重点阅读 |
| --- | --- |
| OpenTelemetry Collector | 数据接入、处理管道、扩展组件 |
| Apache Kafka | Topic、Partition、Producer、Consumer |
| Apache Flink | 状态计算、事件时间、Checkpoint |
| Apache Iceberg | 表格式、Schema 演进、分区演进 |
| Prometheus | 时间序列模型和标签设计 |
| Grafana Loki | 日志标签和基数治理 |
| OpenLineage | 数据血缘和作业运行元数据 |
| OpenMetadata | 元数据目录、数据质量、血缘 |

**本期核验的关键技术事实**：

• OpenTelemetry Collector 采用 Receiver、Processor、Exporter 等组件组成数据管道，支持多条 Pipeline；

• Kafka 通过事件流、Topic 和 Partition 组织数据，生产者与消费者解耦，支持持久化和多消费者订阅；

• Flink 通过状态和 Checkpoint 支持流处理故障恢复；端到端 Exactly-once 还要求数据源可重放、Sink 具备事务性或幂等性；

• Iceberg 支持表 Schema 和分区布局演进，适合大规模分析数据集；

• Loki 的高基数标签会导致索引和数据流数量膨胀，官方建议优先使用稳定、低基数标签。

## 十六、本篇总结：从可观测性走向智能运维数据底座

本篇围绕智能运维数据平台，建立了从多源数据接入到统一数据治理、存储、计算和服务的完整技术体系。需要重点沉淀六项平台能力：

1. **统一接入能力**：解决不同运维系统的数据接入和协议适配问题。

2. **统一数据模型**：解决资源、指标、日志、链路、事件和工单数据的语义不一致问题。

3. **统一存储与计算**：根据数据特征建设实时、离线和历史数据处理能力。

4. **统一数据治理**：建立数据标准、数据质量、元数据、血缘和生命周期管理。

5. **统一数据服务**：为监控、告警、故障诊断和智能体提供标准化数据接口。

6. **统一安全治理**：实现数据分类分级、访问控制、脱敏、审计和安全留痕。

整个系列的技术演进：第 01 篇明确体系 → 第 02 篇建设可观测性采集 → 第 03 篇建设统一数据底座 → 第 04 篇建设 CMDB 与知识图谱 → 第 05 篇 AIOps 算法 → 第 06 篇故障诊断与根因分析 → 第 07 篇大模型与 RAG → 第 08 篇智能运维 Agent → 第 09 篇自动化与自愈 → 第 10 篇自治运维平台架构。

其中第 03 篇和第 04 篇有一个重要的分工：

• 第 03 篇重点解决数据如何汇聚、治理、存储和服务；

• 第 04 篇重点解决资源对象如何建模、资源关系如何表达、运行数据如何映射到资源拓扑，以及如何进一步形成运维知识图谱。

> **小结**：数据平台提供数据基础，CMDB 提供资源语义，知识图谱提供关系推理基础。三者共同构成后续 AIOps 和智能运维 Agent 的上下文基础。

> **小结**：第 04 篇《CMDB 与运维知识图谱——从资源模型到关系推理》，将深入资源建模、依赖拓扑、变更历史与知识图谱构建，把本篇汇聚的数据进一步赋予资源语义与关系推理能力。
