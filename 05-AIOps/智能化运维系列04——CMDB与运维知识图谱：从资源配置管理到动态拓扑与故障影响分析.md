# 智能化运维系列04——CMDB与运维知识图谱：从资源配置管理到动态拓扑与故障影响分析

> 第 01 篇建立体系全景，第 02 篇解决可观测数据采集，第 03 篇建设统一数据底座，本篇在统一数据之上建立**资源语义与关系推理能力**。
> **核心问题**：平台已经能采集 CPU、内存、磁盘、MySQL 连接数、Redis 命中率，也能产生告警。但当数据库故障时，平台能否准确回答——它运行在哪台服务器？哪些应用依赖它？影响哪些业务？故障前有无配置变更？哪些告警属于同一传播链？当前该优先查哪个资源？
> **核心判断**：CMDB 解决"有什么资源、资源是什么、资源之间是什么关系"；运维知识图谱进一步解决"资源、事件、变更、告警、知识之间如何关联，以及如何利用这些关系分析和推理"。CMDB 是资源事实和配置关系的核心管理基础，知识图谱是面向分析与推理的关联模型。

## 破题：数据库告警响了，却没人说得清影响了谁

凌晨，数据库连接数告警响了。值班人员打开监控，看到连接数曲线一路上扬；再打开 CMDB，查到这台数据库运行在某台虚拟机上；想进一步知道"哪些应用依赖它、会波及哪个业务"，却发现 CMDB 里只有一堆孤立的资源记录，没有依赖关系。于是只能在群里问："这个库是谁在用？"

这就是很多 CMDB 的真实处境——建了一堆资源数据，却回答不了故障时的关键问题。原因往往不是数据不全，而是**关系没建起来**：资源之间怎么承载、怎么依赖、怎么归属，没有被准确表达和维护。

这篇文章按工程建设顺序展开：资源模型 → 资源关系 → 数据关联 → 动态拓扑 → 知识图谱 → 故障影响分析。目标是把 CMDB 从静态资产台账，建设成能支撑智能诊断的关系基础。

## 一、CMDB 在智能运维体系中的定位

### 1.1 从资产台账到配置管理

CMDB（Configuration Management Database，配置管理数据库）并不只是服务器资产台账。资产台账关注资产编号、型号、采购日期、责任部门等静态信息；CMDB 还需要管理资源的运行属性、部署关系、依赖关系、配置状态和生命周期。

例如一台服务器不仅要记录主机名、IP、操作系统、CPU、内存、所属机房、机柜、责任人和部门，还需要知道：当前运行哪些虚拟机、部署了哪些数据库和中间件、哪些应用依赖这些数据库、哪些监控指标属于它、哪些告警/变更/工单与它有关。

> **小结**：CMDB 应该从静态资源登记系统，发展为统一的**资源配置管理和关系管理能力**。

### 1.2 CMDB、资产管理、监控和知识图谱的边界

| 系统/能力 | 核心问题 | 主要管理内容 |
| --- | --- | --- |
| 资产管理 | 资产归谁、价值多少 | 资产编号、采购、折旧、责任部门 |
| CMDB | 当前有哪些配置项、如何关联 | 配置项、属性、关系、生命周期 |
| 监控系统 | 资源运行得怎么样 | 指标、日志、链路、告警 |
| ITSM | 运维工作如何管理 | 事件、问题、变更、工单 |
| 运维知识图谱 | 多类对象有什么关联和推理关系 | 资源、事件、变更、知识、依赖和影响 |

这几类系统不是相互替代关系，而是共同构成运维管理体系。

### 1.3 CMDB 在智能运维中的位置

智能运维应用层（故障诊断、影响分析、智能 Agent）向下依赖运维知识图谱，图谱建立在 CMDB 资源模型和事件知识模型之上，统一资源关系再向下对接监控、ITSM 和自动化平台。

> **小结**：CMDB 是资源事实和配置关系的核心管理基础，知识图谱是面向分析与推理的关联模型。并不是所有 CMDB 都必须使用图数据库，也不是引入图数据库就自动形成了知识图谱。

## 二、CMDB 核心模型：配置项、属性、关系与生命周期

### 2.1 什么是配置项（CI）

CI（Configuration Item，配置项）是纳入配置管理范围、需要识别、记录和维护的资源或服务对象。常见配置项包括：

| 分类 | 配置项示例 | 主要管理内容 |
| --- | --- | --- |
| 物理基础设施 | 物理服务器、存储设备、网络设备 | 硬件配置、位置、管理地址 |
| 虚拟化资源 | 虚拟机、虚拟化集群 | vCPU、内存、虚拟磁盘、宿主机 |
| 操作系统 | Linux、Windows 服务器实例 | 版本、内核、主机名、系统状态 |
| 数据库 | MySQL、Oracle、PostgreSQL | 实例、版本、端口、集群角色 |
| 中间件 | Redis、Kafka、Nginx、Tomcat | 实例、集群、节点、监听端口 |
| 应用资源 | 应用系统、应用组件 | 系统归属、部署环境、负责人 |
| 微服务资源 | 服务、服务实例 | 服务名称、版本、实例、调用关系 |
| 业务资源 | 业务系统、业务模块 | 业务归属、重要级别、影响范围 |

配置项范围不是越大越好。建议以"是否需要独立识别、是否需要独立管理、是否需要建立关系、是否需要参与运维分析"为判断依据。例如一台物理服务器通常是一个 CI，运行在服务器上的 MySQL 实例通常是另一个 CI，而 MySQL 的普通配置参数可作为实例属性；如果数据库集群每个节点需要独立监控和处置，则每个节点都应有独立 CI。

### 2.2 CMDB 的核心数据模型

建议采用四个核心对象：**配置项 CI**（唯一标识/名称/类型/状态/环境/责任人）、**CI 属性**（IP/CPU/内存/版本/端口）、**CI 关系**（运行于/部署于/依赖于/连接到）、**CI 生命周期**（待确认/在用/维护/下线/归档）。

其中，**配置项属性与配置项关系必须分开管理**。不能把所有关系都作为 CI 的一般属性保存——例如在服务器上加一个 `mysql_instance_id` 字段虽然简单，却难以表达"一台服务器部署多个数据库""一个数据库集群包含多个节点"这类复杂关系。

### 2.3 配置项基础字段设计

建议所有 CI 继承统一基础字段，再按资源类型扩展专属属性：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| ci_id | VARCHAR | 平台内部唯一标识 |
| ci_code | VARCHAR | 配置项编码 |
| ci_name | VARCHAR | 配置项名称 |
| ci_type / ci_subtype | VARCHAR | 配置项类型/子类型 |
| environment | VARCHAR | 生产、测试、开发等环境 |
| lifecycle_status | VARCHAR | 生命周期状态 |
| operational_status | VARCHAR | 运行状态 |
| owner_org_id / owner_user_id | VARCHAR | 责任部门/责任人 |
| source_system / source_key | VARCHAR | 权威来源系统/原始标识 |
| first_discovered_at / last_seen_at | DATETIME | 首次发现/最近发现时间 |
| last_updated_at | DATETIME | 最近更新时间 |
| version | BIGINT | 数据版本 |
| created_at / updated_at | DATETIME | 创建/修改时间 |

这里建议区分两个状态：**lifecycle_status**（资源管理生命周期，如在用/维护/下线）与 **operational_status**（当前运行状态，如正常/异常/未知）。一台服务器可以处于"在用"生命周期，但运行状态为"异常"，两者不能混用。

### 2.4 属性模型：固定字段与扩展属性

不同资源类型属性差异很大：物理服务器有 CPU 型号、物理内存、机架位置；虚拟机有 vCPU、虚拟内存、宿主机；MySQL 有实例端口、版本、主从角色；Redis 有实例模式、端口、集群角色、内存配置。不建议把所有字段放一张宽表，也不建议把所有属性无约束存成 JSON。可采用混合模型：

```
ci_base                 配置项基础表    │    ├── ci_server            服务器扩展属性    ├── ci_virtual_machine   虚拟机扩展属性    ├── ci_mysql_instance    MySQL扩展属性    ├── ci_redis_instance    Redis扩展属性    │    └── ci_ext_attribute     扩展属性表（受Schema约束）
```

原则：高频查询/过滤/关联的属性优先结构化字段；类型差异明显的用类型扩展表；不常查询、变化快的非关键属性用受 Schema 约束的 JSON 扩展；属性定义应记录数据类型、单位、是否必填、是否可编辑、来源系统和敏感级别。例如 `memory_total` 必须明确单位是 Byte、MiB 还是 GiB。

## 三、四类重点运维对象的资源模型设计

### 3.1 物理服务器模型

物理服务器是基础设施层的核心配置项。建议模型：

| 属性 | 字段编码 | 类型 | 示例 |
| --- | --- | --- | --- |
| 主机名 | hostname | String | db-host-01 |
| 管理 IP | management_ip | String | 10.10.1.11 |
| CPU 型号/核数 | cpu_model / cpu_cores | String / Integer | Kunpeng / 64 |
| 内存容量 | memory_total_bytes | Long | 274877906944 |
| 操作系统及版本 | os_name / os_version | String | Linux |
| 序列号 / 厂商 | serial_number / manufacturer | String | SN001 |
| 机房 / 机柜 | idc_id / rack_id | String | IDC001 / RACK001 |
| 资产编号 | asset_code | String | ASSET001 |

身份识别建议：① 优先使用经核实的硬件序列号或资产唯一标识；② 辅助使用管理 IP、主机名、厂商和型号；③ 不能仅以 IP 作为唯一标识（IP 可能变更或复用）；④ 对虚拟化环境中硬件序列号、克隆机器等特殊情况，增加来源标识和识别规则。

### 3.2 虚拟机模型

虚拟机属于计算资源配置项，需与底层宿主机建立明确关系。核心属性：虚拟机名称、`vm_uuid`（虚拟化平台 UUID）、vCPU 数量、内存容量、虚拟磁盘容量、操作系统、IP 地址数组、虚拟化平台类型，以及宿主机**关系字段**。

重点关系：`物理服务器 HOST001 ──HOSTS──> 虚拟机 VM001`。注意虚拟机迁移后宿主机关系会变化，但虚拟机本身仍是同一个 CI，因此宿主机关系应是**动态关系**，不能把宿主机 ID 永久固化为虚拟机身份属性。

### 3.3 MySQL 实例模型

MySQL 建议区分数据库产品、数据库服务、数据库实例和实例节点。至少需要明确：MySQL 实例（能独立连接、监控和管理的运行实例）、MySQL 节点（集群或复制架构中的成员）、MySQL 集群（多节点组成的高可用或读写架构）。

| 属性 | 字段编码 | 示例 |
| --- | --- | --- |
| 实例名称/ID | instance_name / instance_uuid | order-mysql-01 / MYSQL001 |
| 连接地址/端口 | endpoint / port | 10.10.1.21 / 3306 |
| 版本 | version | 8.0.x |
| 运行模式/节点角色 | deployment_mode / node_role | Standalone / Primary |
| 数据目录 | data_directory | /data/mysql |
| 最大连接数 | max_connections | 1000 |
| 所属集群 | cluster_id | MYSQL-CLUSTER-01 |

对数据库集群，应进一步管理集群与节点关系、主从复制关系、读写角色、复制状态、高可用切换状态、监听地址与实际节点地址的映射。

> **小结**：特别注意：应用连接的可能是 VIP、代理地址或负载均衡地址，而非某个 MySQL 节点 IP，因此需要把**连接入口与实际数据库节点分开建模**。

### 3.4 Redis 实例模型

Redis 同样需要区分实例、节点和集群。核心属性：实例名称/ID、地址、端口、版本、运行模式（如 Cluster）、节点角色、最大内存、持久化模式（AOF/RDB）、所属集群。

Redis 需特别关注：单机/主从/哨兵/Cluster 等部署模式、主从复制关系、Cluster 分片与节点关系、主节点与副本角色变化、连接入口与实际节点对应关系。Redis Cluster 中客户端可能通过集群节点发现机制访问多个节点，因此不能只记录一个 IP 和端口就认为完整描述了集群。

### 3.5 四类资源模型的统一关系

将四类对象组合：`物理服务器 ─HOSTS→ 虚拟机 ─RUNS_ON→ 操作系统 ─RUNS_INSTANCE→ MySQL实例/Redis实例 ─DEPENDS_ON→ 应用服务 ─BELONGS_TO→ 业务系统`。

这是简化示意。生产环境中 MySQL、Redis 可能运行在不同虚拟机或物理服务器上，应用也可能依赖多个数据库实例。

> **小结**：更重要的是，资源关系必须来自真实发现、配置或经确认的业务依赖，**不能因为两个资源处于同一网段就推断它们存在业务依赖**。

## 四、资源关系模型：从资源清单到资源拓扑

### 4.1 为什么关系比属性更重要

假设 CMDB 记录了 100 台物理服务器、300 台虚拟机、50 个 MySQL 实例、80 个 Redis 实例、30 个应用系统——这些数据只能说明平台掌握了资源清单，却不能说明应用与数据库之间的依赖关系。没有关系模型，就无法回答：哪台服务器承载这个数据库？哪个应用依赖它？数据库故障影响哪些应用？一台宿主机故障影响多少虚拟机？一个中间件集群故障影响哪些业务？

> **小结**：CMDB 的核心价值不仅在于记录 CI，更在于准确维护 CI 之间的关系。

### 4.2 关系模型设计

建议将关系分六大类：

| 关系分类 | 关系编码 | 含义 | 示例 |
| --- | --- | --- | --- |
| 物理承载 | HOSTS | 物理设备承载虚拟资源 | 服务器→虚拟机 |
| 部署运行 | RUNS_ON | 软件或实例运行在计算资源上 | MySQL→虚拟机 |
| 业务依赖 | DEPENDS_ON | 一个服务依赖另一个服务 | 应用→MySQL |
| 网络连接 | CONNECTS_TO | 两资源间存在网络连接 | 应用→Redis |
| 集群组成 | MEMBER_OF | 节点属于某集群 | MySQL 节点→集群 |
| 业务归属 | BELONGS_TO | 资源归属于业务或组织 | 应用→业务系统 |

**关系方向必须统一**。例如 `应用服务 ─DEPENDS_ON→ MySQL实例 ─RUNS_ON→ 虚拟机 ─HOSTED_ON→ 物理服务器`。反向遍历即可得到"物理服务器 →（受影响的）虚拟机 → 数据库 → 应用服务"。

注意：RUNS_ON 与 HOSTED_ON 语义上描述同一关系的不同方向，建议选择一种标准编码作为存储关系，查询时按方向遍历，**不要无意义地重复保存两条边**。

### 4.3 关系必须包含属性

关系不是简单的两个 CI 之间的连接，建议至少包含：`relation_id`、`source_ci_id`、`target_ci_id`、`relation_type`、`relation_direction`、`valid_from`、`valid_to`、`discovery_source`、`confidence`、`status`、`confirmed_by`、`last_verified_at`。

为什么要记录生效时间？因为资源关系是动态的：虚拟机从服务器 A 迁移到 B、MySQL 主从切换、Redis Cluster 调整节点、应用发布后新增数据库依赖。如果只覆盖原关系，就无法准确分析历史故障。建议采用带有效时间的关系模型，支持查询"当前拓扑"和"故障发生时的历史拓扑"。

### 4.4 关系表 SQL 设计示例

relation_id VARCHAR(64) PRIMARY KEY,

target_ci_id VARCHAR(64) NOT NULL,

### 4.5 关系建模需要避免的几个问题

• **问题一**：把所有关系都定义成依赖关系。虚拟机运行在服务器上，是承载关系，不是业务依赖关系，二者对故障影响分析含义不同。

• **问题二**：没区分逻辑资源与物理资源。应用依赖的可能是数据库服务入口，底层才是具体节点，不能简单把应用直接绑定到某台物理服务器。

• **问题三**：没记录关系来源。自动发现的网络连接、人工维护的业务依赖、链路推断的调用关系可信度不同，不能一视同仁。

• **问题四**：只维护当前关系。没有历史关系，就无法准确重建过去故障发生时的资源拓扑。

## 五、CMDB 与 Prometheus、OpenTelemetry、ITSM 的数据关联

CMDB 不能孤立运行，必须与监控、可观测性和 ITSM 建立统一关联。本节解决一个工程问题：**如何让监控系统采集的数据准确关联到 CMDB 中的配置项**。

### 5.1 统一资源标识设计

建议在 CMDB 中为每个 CI 分配平台内部唯一 ID：`ci_id = RSC-20261120-000001`。不同系统保留各自原始标识，通过映射表关联：Prometheus 的 `instance=10.10.1.21:9100`、虚拟化平台的 `vm_uuid=UUID001`、MySQL 采集器的 `instance_id=mysql-01`、ITSM 的 `configuration_item=CI001`、自动化平台的 `target_id=host-01`，都映射到统一 CMDB ID。

CREATE TABLE cmdb_ci_external_id (

id VARCHAR(64) PRIMARY KEY,

ci_id VARCHAR(64) NOT NULL,

source_system VARCHAR(64) NOT NULL,

external_type VARCHAR(64) NOT NULL,

external_id VARCHAR(256) NOT NULL,

created_at TIMESTAMP NOT NULL,

updated_at TIMESTAMP NOT NULL

);

CREATE UNIQUE INDEX uk_ci_external_identity

ON cmdb_ci_external_id(source_system, external_type, external_id);

### 5.2 CMDB 与 Prometheus 关联

Prometheus 用指标名称和标签集合唯一标识一条时间序列，标签值变化会产生新序列。采集端的 `instance` 通常是采集目标地址，**不等于 CMDB 资源 ID**。建议通过采集目标发现配置或服务发现元数据，将 CMDB 资源标识注入指标标签：

100 - (

avg by (instance, cmdb_ci_id) (

rate(node_cpu_seconds_total{mode="idle", job="node-exporter", environment="production"}[5m])

) * 100

)


但需特别注意：`cmdb_ci_id` 应稳定，不随 IP 变更而改变；不要把请求 ID、用户 ID、随机会话 ID 等高基数信息作为标签；资源 ID 标签也会增加时间序列数量，必须评估基数；如果资源规模很大，可考虑通过监控查询服务做资源映射，而不是无条件给所有指标加标签。

### 5.3 CMDB 与 OpenTelemetry 关联

OpenTelemetry 定义了资源属性和语义约定描述产生遥测数据的服务和资源。服务语义约定包括 `service.namespace`、`service.name`、`service.instance.id`、`service.version`，官方约定将逻辑服务与服务实例区分，并要求同一命名空间和服务名称下的实例标识能区分各实例。

| OTel 属性 | CMDB 对象 | 说明 |
| --- | --- | --- |
| service.namespace | 应用系统 | 业务系统或命名空间 |
| service.name | 微服务 | 逻辑服务名称 |
| service.instance.id | 服务实例 | 唯一服务实例 |
| service.version | 服务版本 | 当前运行版本 |
| host.name / host.id | 主机 | 运行主机及标识 |
| deployment.environment.name | 部署环境 | 生产、测试等 |

不能将 `service.name` 直接当作 CI 唯一标识，因为同一逻辑服务可能有多个实例。建议采用 `service.namespace + service.name → 微服务 CI`，其下再由 `service.instance.id` 区分多个服务实例。对无法准确识别来源资源的遥测数据，不要强行生成错误映射，应保留原始属性并标记映射状态。

### 5.4 CMDB 与 ITSM 关联

ITSM 中的事件、问题、变更和工单都应关联到 CMDB 资源。以数据库连接数异常告警为例：① 告警携带 `cmdb_ci_id`；② 告警中心查询对应 CI 及拓扑关系；③ 事件单记录受影响资源；④ 故障工单记录处置过程；⑤ 如需调整配置则关联变更单；⑥ 变更完成后记录执行结果并观察指标是否恢复。

建议建立统一关联字段：`ci_id`、`event_id`、`incident_id`、`problem_id`、`change_id`、`work_order_id`、`automation_execution_id`，从而形成完整的运维事件链。

### 5.5 统一关联架构

Prometheus、OpenTelemetry、日志平台、ITSM、自动化平台统一接入资源映射服务，转换为 CMDB 统一 CI，再经资源关系服务进入运维知识图谱，最终支撑故障诊断。

> **小结**：建议由 CMDB 提供统一资源查询接口，由资源映射服务负责外部 ID 转换，由关系服务负责拓扑查询——避免每个业务系统分别维护一套资源映射逻辑。

## 六、资源发现、数据对账与冲突治理

### 6.1 CMDB 数据从哪里来

| 数据来源 | 可发现/同步的数据 | 适合承担的职责 |
| --- | --- | --- |
| 资产管理系统 | 资产编号、采购信息、责任部门 | 资产信息来源 |
| 虚拟化管理平台 | 虚拟机、宿主机、虚拟化关系 | 虚拟化资源发现 |
| 主机采集 Agent | 主机名、IP、操作系统、CPU、内存 | 主机运行属性 |
| Prometheus Exporter | CPU、内存、磁盘、连接数等 | 运行指标采集 |
| MySQL/Redis 采集器 | 版本、实例状态、角色、复制状态 | 实例发现与监控 |
| OpenTelemetry | 服务、实例、调用关系 | 应用和服务拓扑发现 |
| ITSM | 事件、变更、工单、责任信息 | 运维流程关联 |
| 人工录入 | 业务归属、责任关系、特殊配置 | 补充自动发现盲区 |

需区分三个概念：**资源发现**（发现环境中实际存在的资源）、**资源识别**（判断发现的资源对应哪个 CI）、**资源对账**（比较多来源数据、处理差异冲突）。发现不等于入库，入库也不意味着资源已准确识别。

### 6.2 推荐的资源发现流程

数据源配置 → 启动发现任务 → 获取资源数据 → 数据标准化 → 资源身份识别 →（已存在 CI → 属性对账 → 冲突治理 / 未发现 CI → 新建候选 CI → 规则校验）→ 更新 CMDB → 建立资源关系 → 记录发现结果。

生产环境建议增加**发现数据暂存区**：数据源 → 暂存区（字段校验、身份识别、重复检测、属性冲突检测、关系校验）→ CMDB 正式数据，避免未经验证的发现结果直接覆盖核心数据。

### 6.3 资源身份识别：如何判断是不是同一个 CI

假设采集到两条数据：`{hostname: db-host-01, management_ip: 10.10.1.21, serial_number: SN001}` 和 `{hostname: db-host-01, management_ip: 10.10.1.22, serial_number: SN001}`——IP 变了但序列号相同。如果按 IP 识别，就会新增一条 CI，导致同一台服务器重复记录。

建议采用分层身份识别规则：

| 资源类型 | 优先识别依据 | 辅助识别依据 |
| --- | --- | --- |
| 物理服务器 | 硬件序列号、资产唯一编号 | 厂商、型号、主机名、管理 IP |
| 虚拟机 | 虚拟化平台 UUID | 平台 ID、管理域、虚拟机名称 |
| MySQL 实例 | 实例注册 ID 或平台实例 ID | 管理地址、端口、数据目录 |
| Redis 实例 | 实例注册 ID 或平台实例 ID | 地址、端口、集群 ID |
| 微服务 | 服务命名空间、服务名称 | 环境、实例 ID、部署标识 |

这些识别字段不是绝对通用的标准，必须结合实际资源管理系统制定。尤其 MySQL 和 Redis 仅用 IP 和端口，可能把代理入口、VIP、容器映射地址和实际服务实例混为一谈。

### 6.4 属性冲突治理：谁的数据最可信

假设服务器内存来自三个系统：资产管理系统 256GB（30 天前）、主机 Agent 512GB（5 分钟前）、人工录入 128GB（10 天前），该用哪个？建议建立**数据源权威规则（Reconciliation Rules）**：

| 属性 | 权威来源 | 其他来源用途 |
| --- | --- | --- |
| 资产编号、序列号 | 资产管理系统或硬件发现 | 交叉核验 |
| CPU 和内存 | 主机 Agent 或硬件管理接口 | 交叉核验 |
| 虚拟机宿主机 | 虚拟化管理平台 | 关系核验 |
| MySQL 运行版本 | 数据库采集器 | 交叉核验 |
| Redis 主从角色 | Redis 发现接口 | 交叉核验 |
| 业务责任部门 | 组织或业务管理系统 | 交叉核验 |
| 应用与数据库依赖 | 应用配置、调用链、业务确认 | 交叉核验 |

三个必须落实的规则：① 一个属性明确一个主要权威来源，必要时设备用来源；② 权威来源变化必须有审批和记录；③ 冲突**不能简单采用"最后更新时间较晚的数据覆盖"**。

> **小结**：ServiceNow 的 CMDB Identification and Reconciliation（IRE）提供了身份识别、数据协调、去重和来源写入权限控制的参考机制（其 2026 年 3 月更新的 Australia 版本文档介绍了相应框架）。这类机制值得借鉴，但不意味着必须采用该产品——自研 CMDB 也应实现类似的识别规则、属性权威规则和重复数据治理机制。

### 6.5 资源生命周期管理

生命周期：待发现 → 待确认 → 在用 →（维护中 / 异常 / 变更中）→ 下线 → 归档。生命周期和运行状态应分开管理：服务器可处于"在用"但运行"异常"；数据库可"维护中"但仍正常提供服务；资源已下线但历史告警和变更记录仍需保留。

建议增加资源失联治理：连续若干次发现失败标记待核查；超期未发现进入疑似失效；经业务责任人确认后才能正式下线；下线后保留历史关联和审计记录。**不能因为一次采集失败就直接删除 CI**。

## 七、拓扑架构：从静态资源关系到动态运行拓扑

### 7.1 静态拓扑与动态拓扑

静态拓扑主要来源于 CMDB（服务器承载哪些虚拟机、虚拟机运行哪些数据库、应用依赖哪些中间件、资源归属哪个业务系统）；动态拓扑主要来源运行时观测（实际发生哪些调用、哪些实例在通信、当前数据库主从角色、哪个 Redis 节点承载请求、是否出现新依赖）。两者结合才形成较完整的运维拓扑。

| 维度 | 静态拓扑 | 动态拓扑 |
| --- | --- | --- |
| 主要来源 | CMDB、配置管理、人工确认 | Trace、网络观测、服务发现 |
| 关系性质 | 配置关系、计划关系 | 实际运行关系 |
| 更新方式 | 变更和定期发现 | 持续采集和计算 |
| 主要用途 | 资源管理、影响范围分析 | 实际调用分析、异常传播分析 |
| 主要问题 | 数据可能滞后 | 观测范围可能不完整 |

例如 CMDB 记录应用 A 依赖 MySQL B，但运行时 Trace 没发现调用，可能原因包括：该时间窗内无实际调用、链路采样未覆盖、数据库调用未埋点、访问经过代理或中间层、CMDB 依赖已过期。**不能简单把"没观察到调用"判定为"不存在依赖"**。

### 7.2 动态拓扑的总体架构

静态资源数据经 CMDB 形成静态资源拓扑；动态运行数据（Trace、网络连接）和变更事件（ITSM）一并进入拓扑关联引擎，产出动态拓扑服务，向上支撑服务依赖、资源状态、故障传播分析和故障影响分析。

### 7.3 动态拓扑的数据模型

建议将拓扑边分为：`CONFIGURED_DEPENDENCY`（配置声明依赖）、`OBSERVED_CALL`（实际观察调用）、`NETWORK_CONNECTION`（实际网络连接）、`HOSTED_ON`（承载关系）、`MEMBER_OF`（集群成员）。并为动态关系增加属性：`source_type`、`first_observed_at`、`last_observed_at`、`observation_count`、`confidence`、`environment`、`valid_from`、`valid_to`。

> **小结**：建议保留关系来源类型，避免把人工配置的依赖和运行时观测到的调用关系混为一谈。

### 7.4 拓扑数据如何形成

1. 从 CMDB 获取资源节点和静态关系；

2. 从 OpenTelemetry 获取服务和调用数据；

3. 根据服务标识、实例标识和资源映射规则匹配 CMDB；

4. 将观测到的调用关系转换为动态拓扑边；

5. 与静态关系比对；

6. 对新关系、冲突关系、过期关系分类；

7. 将确认后的关系更新到拓扑服务。

OpenTelemetry 服务语义约定明确区分逻辑服务与服务实例，可作为动态拓扑关联的基础。

### 7.5 动态拓扑需要解决的三个问题

**服务实例频繁变化**：容器重建后实例 ID 变化但逻辑服务不变。解决：建立逻辑服务 CI 和服务实例 CI 两级模型，避免把实例变化误判为服务新增。

**关系存在时间差**：主从切换后主节点关系变化。解决：关系采用有效时间模型，保留切换前后的角色关系。

**动态发现存在噪声**：健康检查、监控探测、代理转发也会产生网络连接。解决：建立关系识别规则，区分业务调用、基础设施连接和探测流量，不把所有网络连接都当业务依赖。

## 八、从 CMDB 到运维知识图谱

### 8.1 CMDB 与知识图谱的区别

CMDB 主要维护资源配置事实。知识图谱进一步将资源、服务、告警、事件、变更、工单、知识案例等对象连接起来，形成可查询、可分析的关联网络。例如 MySQL 实例既"运行于"虚拟机，又"产生"连接数告警、"关联"参数变更、"创建"故障工单、"匹配"历史故障案例——此时图谱中不仅有"资源关系"，还有"资源与运维事件之间的关系"。

### 8.2 知识图谱的核心实体设计

| 实体分类 | 实体类型 | 示例 |
| --- | --- | --- |
| 资源实体 | 服务器、虚拟机、数据库、Redis、应用、微服务 | MySQL-01 |
| 事件实体 | 告警、事件、故障、异常 | 数据库连接数异常 |
| 变更实体 | 发布、配置变更、扩容、迁移 | 数据库连接池调整 |
| 流程实体 | 工单、审批、执行任务 | 故障处理工单 |
| 知识实体 | 故障案例、操作手册、技术规范 | MySQL 连接数异常处理手册 |

建议统一实体基础属性：`entityId`、`entityType`、`entityName`、`sourceSystem`、`sourceId`、`eventTime`、`version`。资源实体与事件实体生命周期不同，不应把告警和工单直接作为普通 CI 处理——CMDB 负责资源 CI，知识图谱或事件关联模型负责跨领域实体及其关系。

### 8.3 知识图谱关系设计

| 起点实体 | 关系 | 终点实体 |
| --- | --- | --- |
| 应用服务 | DEPENDS_ON | MySQL 实例 |
| MySQL 实例 | RUNS_ON | 虚拟机 |
| 虚拟机 | HOSTED_ON | 物理服务器 |
| 告警事件 | OCCURS_ON | MySQL 实例 |
| 变更单 | CHANGES | MySQL 实例 |
| 工单 | HANDLES | 告警事件 |
| 故障案例 | SIMILAR_TO | 告警事件 |
| 知识文档 | APPLIES_TO | MySQL 实例类型 |

其中 `SIMILAR_TO` 属于分析或知识关联，不应被当作确定性的资源配置关系。

### 8.4 图数据库还是关系数据库

**方案 A：关系型数据库实现资源关系。** 适合 CI 数量和关系规模可控、主要是 1~3 层关系查询、现有系统已用关系库、需要事务与复杂业务查询的场景。示例：

SELECT

r.relation_type,

target.ci_id,

target.ci_name

FROM cmdb_ci_relation r

INNER JOIN cmdb_ci target

ON r.target_ci_id = target.ci_id

WHERE r.source_ci_id = 'RSC-000001'

AND r.relation_status = 'ACTIVE'

AND r.valid_from <= NOW()

AND (r.valid_to IS NULL OR r.valid_to > NOW())

AND (r.confidence IS NULL OR r.confidence >= 0.8);

```

```

多层递归查询可采用递归 CTE（数据库支持时）、应用层分层查询或专门拓扑服务。优点是系统简单、便于集成，缺点是多层遍历可能需要较多 JOIN 和递归。

**方案 B：图数据库实现拓扑关系。** 图数据库将实体表示为节点、关系表示为边：

(:Application)

-[:DEPENDS_ON]->

(:MySQL)

-[:RUNS_ON]->

(:VirtualMachine)

-[:HOSTED_ON]->

(:PhysicalServer)

```

```

Neo4j 的属性图模型支持节点、带类型和方向的关系及属性，Cypher 可用于匹配遍历：

MATCH (app:Application)-[:DEPENDS_ON]->(:MySQL)-[:RUNS_ON]->(:VirtualMachine)-[:HOSTED_ON]->(host:PhysicalServer {ci_id: 'PS001'})

RETURN DISTINCT app.ci_id, app.name;

```

```

查询某台服务器故障影响的应用：

MATCH path = (app:Application)-[:DEPENDS_ON*1..3]->(resource)-[:RUNS_ON|HOSTED_ON*0..2]->(host:PhysicalServer {ci_id: 'HOST001'})

WHERE all(r IN relationships(path) WHERE r.status = 'ACTIVE')

RETURN app.ci_id AS appId, path

LIMIT 200;

```

```

以上第二段是表达思路的示例查询，实际生产模型应统一边方向，避免混合方向导致路径不符合业务语义，必要时使用多个明确的路径模式。

### 8.5 两种方案如何选择

| 对比项 | 关系数据库 | 图数据库 |
| --- | --- | --- |
| 基础资源管理 | 非常适合 | 可以实现 |
| 属性/事务/业务管理 | 非常适合/成熟 | 支持/依产品能力 |
| 简单关系查询 | 适合 | 适合 |
| 多层拓扑遍历 | 需递归或多次查询 | 通常更自然 |
| 复杂路径分析 | 实现复杂度较高 | 更适合 |
| 现有系统集成 | 通常更容易 | 需增加同步与一致性机制 |
| 运维复杂度 | 可复用现有数据库 | 增加新组件和治理成本 |

> **小结**：对于正在建设的一体化运维运营平台，不建议一开始就把 CMDB 整体迁移到图数据库。更稳妥的路线是：① 先用关系库建立规范 CI 和关系模型；② 建立统一拓扑查询服务；③ 按实际规模和查询压力开展图数据库验证；④ 当多层遍历、复杂路径分析成为瓶颈再引入图数据库；⑤ 图数据库作为分析型关系存储，CMDB 仍负责配置数据权威管理。这样可避免两个资源中心、两个权威数据源和双向同步不一致。

## 九、故障影响分析：利用资源拓扑识别故障传播范围

### 9.1 故障影响分析的基本原理

假设某台物理服务器故障：`HOST001 ─HOSTED_ON→ VM001 ─→ MySQL实例 / Redis实例 ─→ 应用服务 ─→ 业务系统`。平台可沿关系反向遍历，识别：① 承载的虚拟机；② 虚拟机上运行的数据库和中间件；③ 依赖它们的应用；④ 应用所属业务系统；⑤ 可能受影响的业务范围。

### 9.2 故障影响分析流程

接收故障告警 → 确认故障资源 CI → 查询资源拓扑 → 获取上游和下游 → 判断关系类型 → 过滤失效关系 → 关联业务重要程度 → 计算影响范围 → 生成影响分析报告。

> **小结**：注意：故障影响分析**不意味着所有关联资源都已发生故障**。一台物理服务器故障可能影响其虚拟机，但具体应用是否不可用，还要考虑是否有其他宿主机冗余实例、数据库主备或集群切换能力、应用多实例负载均衡、容灾或降级机制。拓扑传播只提供候选影响范围，必须结合冗余关系和运行状态进一步判断。

### 9.3 影响分析评分模型

可以建立简单的影响风险评分：`R = W_c × C + W_d × D + W_s × S`，其中 C 业务重要程度、D 依赖关系强度、S 资源运行异常程度，各项 0~5 分，权重可按业务设置。该模型适合初步排序，但**不是标准化行业算法**，后续可结合历史故障数据、SLA 和业务影响评估校准。

### 9.4 故障影响分析报告示例

报告内容：故障资源 `HOST001 / 物理服务器`，现象"主机运行状态异常、监控数据中断"，状态"影响范围待确认"；候选影响链路：① HOST001（故障源）② VM001、VM002（承载的虚拟机）③ MySQL001、Redis001（运行于相关虚拟机的实例）④ 应用服务及业务系统（通过依赖识别的候选对象）。以上为演示数据，实际受影响程度需结合集群冗余、实例健康状态和业务请求验证。

### 9.5 从影响分析到根因分析

影响分析回答"一个资源故障可能影响哪些对象"，根因分析回答"多个资源异常最可能是哪个资源或事件导致的"，二者方向不同：影响分析从故障源向业务影响传播，根因分析从多个异常反向寻找共同原因。

例如 MySQL 连接数持续增长 → 连接等待增加 / 应用接口 P95 升高 / 订单服务超时 → 查询变更记录 → 发现参数变更 → 分析时间关系 → 输出候选根因及证据。平台可通过拓扑、告警、指标、变更和历史案例计算候选根因。

> **小结**：但不能仅凭"变更发生在告警之前"就断定变更是根因，还需验证参数变化、数据库行为和应用异常之间是否存在合理因果链。

## 十、实战设计：MySQL 故障的拓扑关联与根因分析

### 10.1 场景背景

某业务订单服务响应时间升高。监控异常：10:05 MySQL 活跃连接数持续增长、10:06 等待连接数增加、10:07 订单服务接口 P95 升高、10:08 超时告警。ITSM 记录：10:00 执行数据库连接参数调整，对象为 MySQL001，操作已完成。

### 10.2 第一步：根据告警定位 CI

{

"eventId": "EVT001",

"resourceId": "RSC-MYSQL-001",

"resourceType": "MYSQL",

"metric": "mysql_global_status_threads_connected",

"value": 180,

"severity": "HIGH",

"eventTime": "2026-11-20T10:05:00+08:00"

}

```

```

告警中心根据 `resourceId` 查询 CMDB，获得 MySQL 实例基本信息。

### 10.3 第二步：获取资源拓扑

查询得到：`MySQL001 → VM001 → HOST001`，以及 `订单服务 → MySQL001`。这样明确数据库所在计算环境及依赖它的应用。

### 10.4 第三步：查询运行数据

通过统一数据服务查询 MySQL 连接数、最大连接数、等待数量、慢查询、数据库 CPU/内存、订单服务 P95 和错误率，按统一时间窗口关联。

### 10.5 第四步：查询变更和历史工单

通过 ITSM 查询 `MySQL001 → 近期变更记录 → 数据库连接参数调整 → 关联变更单 CHG001`，进一步检查修改前后参数值、实际执行时间、是否有操作异常、是否有类似历史故障。

### 10.6 第五步：形成候选根因

{

"eventId": "EVT001",

"resourceId": "RSC-MYSQL-001",

"candidateCauses": [

{

"cause": "数据库连接参数调整可能导致连接行为变化",

"relatedChangeId": "CHG001",

"evidence": [

"变更时间早于异常发生时间",

"数据库连接数持续增长",

"订单服务接口响应时间同步升高"

],

"confidence": "MEDIUM"

}

],

"verificationRequired": true

}

```

```

这里的 MEDIUM 只是示例等级，不代表已验证因果关系。

### 10.7 第六步：生成处置建议并验证

建议：① 检查数据库连接参数调整内容；② 检查应用连接池配置；③ 检查数据库当前连接分布；④ 检查慢查询及锁等待；⑤ 由运维人员确认是否回退变更；⑥ 执行后持续观察连接数、错误率和 P95。

> **小结**：如果需要自动回退，必须经过权限校验和变更审批，不能让诊断 Agent 直接执行高风险操作。

## 十一、工程实施路线：如何建设一套可用的 CMDB

建议不要一开始就建设全量资源模型和完整知识图谱，而是分阶段实施。

**第一阶段：建立核心资源模型（基础）。** 制定 CI 分类编码规范、建立 CI 基础模型、建立服务器/虚拟机/MySQL/Redis 四类模型、建立关系模型、建立外部标识映射、建立生命周期管理。阶段成果：形成统一资源管理基础，能准确识别和管理核心基础设施及数据库资源。

**第二阶段：建设资源发现与治理能力。** 对接虚拟化平台、主机 Agent、MySQL/Redis 采集器；建立身份识别规则、属性权威规则、重复检测和冲突治理、关系自动发现。阶段成果：实现资源自动发现、识别、更新、对账和关系维护。

**第三阶段：建设资源拓扑能力。** 建设关系查询服务、静态拓扑展示；对接 OTel 服务数据和监控告警；建设动态关系更新和历史拓扑；实现故障影响范围分析。阶段成果：从资源台账向资源拓扑演进，能识别故障资源关联对象和候选影响范围。

**第四阶段：建设运维知识图谱。** 扩展告警/事件/变更/工单实体；建立资源与事件关联、历史案例关联；建设多层拓扑查询和路径分析、根因分析数据接口；为智能诊断和 Agent 提供上下文服务。阶段成果：形成资源、运行、事件和知识之间的关联能力，支撑智能故障诊断。

### 11.1 建议的建设模块划分

| 模块 | 子功能 | 优先级 |
| --- | --- | --- |
| CI 模型管理 | 类型、属性、分类、版本 | P0 |
| CI 实例管理 | 新增、修改、查询、下线 | P0 |
| 关系管理 | 关系类型、维护、查询 | P0 |
| 资源映射管理 | 外部 ID、数据源映射 | P0 |
| 资源发现管理 | 发现任务、数据接入、结果确认 | P1 |
| 数据对账管理 | 身份识别、属性冲突、去重 | P1 |
| 生命周期管理 | 状态、下线、归档 | P1 |
| 拓扑管理 | 拓扑查询、展示、历史拓扑 | P1 |
| 动态拓扑 | Trace 关联、运行时关系发现 | P2 |
| 知识图谱 | 事件、变更、工单、知识关联 | P2 |

## 十三、安全与治理：CMDB 必须解决的管理问题

CMDB 数据涉及服务器地址、系统部署关系、数据库实例、网络连接和业务依赖，具有较高安全敏感性。

### 13.1 资源数据权限

按组织划分资源管理范围、按管理域隔离资源、按资源类型控制查看和维护权限、按生产/测试/开发环境控制访问、对敏感属性字段级授权、对批量导出/修改/删除实施审批。

### 13.2 资源关系权限

关系信息有时比单个资源属性更敏感。例如某业务系统依赖哪些数据库、服务器部署在哪个机房、不同业务系统如何调用，可能暴露系统架构。因此：拓扑查询必须权限过滤；不能因为用户有某 CI 权限就自动允许查看其全部关联 CI；跨管理域关系应校验两端访问权限；Agent 查询拓扑必须使用调用用户或服务身份的授权上下文。

### 13.3 数据变更审计

至少记录：CI 创建/修改/下线、关系创建/修改/失效、数据源权威规则变更、资源映射规则变更、批量数据导入、发现任务和自动对账结果、拓扑关系人工确认。审计日志需记录操作人、时间、修改前后值、来源、审批单和结果。

### 13.4 知识图谱安全

知识图谱不是天然安全的数据存储。建议：① 对资源、事件、知识实体分别设权限；② 图查询限制最大遍历深度和返回数量；③ 防止用复杂路径查询获取大量敏感信息；④ 对 Agent 开放只读、受限的拓扑查询工具；⑤ 对拓扑导出和跨域查询留痕；⑥ 对历史版本和失效关系做权限及留存治理。

## 十四、常见建设误区

| 误区 | 实际问题 | 建议 |
| --- | --- | --- |
| CMDB 就是资产台账 | 缺少资源关系和配置管理 | 建立 CI 及关系模型 |
| IP 作为唯一资源 ID | IP 变化/复用导致重复 CI | 建立稳定内部 ID 和外部映射 |
| 所有资源一张宽表 | 字段复杂、模型难维护 | 基础模型 + 类型扩展 |
| 所有关系都是依赖关系 | 无法准确分析故障传播 | 区分承载/部署/依赖/连接 |
| 只记录当前拓扑 | 无法重建历史故障现场 | 采用关系有效时间 |
| 监控指标直接关联资源名称 | 名称重复/变更导致错误映射 | 使用稳定资源 ID |
| 所有动态调用都当业务依赖 | 健康检查和探测产生噪声 | 关系分类与可信度管理 |
| 一开始就建设图数据库 | 增加复杂度和同步成本 | 先建立规范关系模型 |
| Agent 直接查询全量图谱 | 可能越权访问架构信息 | 统一授权和受控工具接口 |

## 十六、本篇总结：CMDB 建设的核心是统一资源语义和关系

本篇从资源管理出发，逐步建立了 CMDB 与运维知识图谱的技术体系，需重点形成七项能力：

1. **统一资源模型**：统一服务器、虚拟机、MySQL、Redis、应用和微服务的 CI 分类及属性。

2. **统一资源标识**：建立平台内部 CI ID 及外部系统标识映射。

3. **统一关系模型**：管理承载、部署、依赖、连接、集群和业务归属关系。

4. **统一数据治理**：建立资源发现、身份识别、属性对账和生命周期管理。

5. **统一动态拓扑**：将 CMDB 静态关系与运行时观测关系结合。

6. **统一知识关联**：关联资源、告警、事件、变更、工单和历史知识。

7. **统一分析能力**：支撑故障影响分析、异常关联和根因定位。

架构演进：资源台账 → 配置项管理（CI）→ 资源关系管理 → 静态资源拓扑 → 动态运行拓扑 → 运维知识图谱 → 故障影响分析 → 智能根因定位。

> **小结**：一个成熟的 CMDB，不是简单地记录资源，而是能够准确表达资源的**身份、属性、关系、状态和历史**。而运维知识图谱的价值，是在此基础上把运行数据、运维事件和业务知识联系起来，让平台具备跨系统关联分析能力。
