# 第六章：数据库工程

> 从单机存储引擎到云原生分布式数据库：先理解数据怎么落盘、事务怎么保证，再谈架构选型与运维。

数据库是业务系统的数据底座，也是最容易被"会用 SQL"掩盖底层机制的一层。一条慢查询背后，可能是索引选错、执行计划突变、锁等待，也可能是 Buffer Pool 被大查询打穿、复制延迟导致的读不一致。

本章围绕关系型数据库的运行机制、云原生架构演进与工程运维展开：既讲清存储引擎、事务与复制这些"不随版本变化"的原理，也覆盖存算分离、弹性扩缩容、分布式事务等在云上部署时必须面对的取舍。

重点不在背参数，而在于**知道每个参数在改什么机制、会付出什么代价、如何验证效果**。

## 学习目标

通过本章的学习与实践，希望能够：

- 理解 InnoDB 的页结构、B+ 树索引与聚簇索引，能读懂执行计划。
- 掌握事务 ACID、隔离级别、MVCC 与锁机制，能分析死锁与锁等待。
- 理解 redo log、undo log、binlog 的分工，以及崩溃恢复与时间点恢复（PITR）。
- 掌握主从复制、半同步与高可用切换的机制和失效场景。
- 理解分库分表、分布式事务与一致性之间的权衡。
- 理解云原生数据库的存算分离、计算弹性与共享存储架构。
- 能通过慢日志、监控指标与系统视图定位问题，并制定备份、容量与变更方案。

## 文档原则

- **机制优先**：解释参数与架构改动的是哪条链路，而不只给配置。
- **数据说话**：性能结论必须有压测或监控数据支撑，标注测试条件。
- **版本可追溯**：注明数据库版本、存储引擎、部署形态（自建 / 云托管 / 云原生）。
- **写清边界**：说明结论适用的数据量、并发量与硬件条件，以及失效场景。
