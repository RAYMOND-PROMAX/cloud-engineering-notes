# Cloud Engineering Notes

**Linux · Cloud · DevOps · Kubernetes · Observability · AI Infra**

一个持续整理中的云计算与基础设施工程知识库，记录技术原理、部署实验、故障分析与工程实践。

这个仓库不仅保存如何安装、配置和使用一项技术，也希望留下更难被命令替代的部分：**如何认识问题、如何作出判断、如何验证结果，以及如何让一次经验在下一次运行中继续发挥作用。**

----

## 01 · 先确认真正需要解决的问题

工程问题往往先以模糊的语言出现：系统很慢、资源不够、流程太繁琐、服务不稳定。这些反馈值得重视，但它们描述的可能是现象，也可能只是使用者对原因的猜测。

“系统慢”不必然意味着算力不足；“需要更多自动化”也不一定意味着必须建设一套新平台。真正影响效率的，可能是请求排队、依赖异常、流程中的一次重复确认，或是部门之间尚未明确的责任边界。

因此，在讨论方案之前，需要先弄清楚：

- **场景**：问题发生在哪里，影响了谁，妨碍了哪一段工作？
- **事实**：哪些是实际观察到的现象，哪些只是推测？
- **需求**：提出的解决办法，是否就是需要实现的目标？
- **标准**：怎样的变化能让使用者和业务方共同确认问题已解决？

把模糊诉求转化为清晰的问题定义，是技术工作真正开始的地方。**先确认做的是正确的事，再讨论如何把它做好。**

## 02 · 沿着系统链路寻找证据

知道一个服务如何启动，与理解它为什么能够稳定工作，是两件不同的事。

一次请求从接入层进入，可能经过网关、应用、缓存、数据库与网络；一个任务从提交到完成，可能涉及队列、调度、资源分配、执行和结果持久化。任何一个环节的状态变化，都可能在另一处表现为延迟、超时或失败。

分析问题时，习惯先建立系统的正常运行路径，再定位异常偏离了哪一步：

1. **明确现象与影响范围**：何时出现、是否持续、哪些请求或任务受到影响。
2. **还原关键链路**：组件各自承担什么职责，请求、数据和状态如何流动。
3. **建立基线并观察**：用 Metrics、Logs、Traces、系统命令或抓包记录可比较的证据。
4. **提出并排除假设**：区分相关现象和真正原因，寻找能够支持或反驳判断的信息。
5. **实施验证**：在风险可控的条件下调整关键变量，观察结果和机制是否一致。

例如，CPU 使用率很高是一个事实，却未必是响应缓慢的根因。需要进一步判断线程是否在等待 I/O、请求是否积压、下游耗时是否增加，以及资源繁忙与用户体验变化是否发生在同一条因果链上。

**指标说明发生了什么，机制帮助解释为什么发生。** 两者结合，才能让判断不只停留在经验上。

## 03 · 在现实约束中选择方案

技术选型不是寻找功能最多、架构最新的答案，而是在目标与约束之间找到适合当前阶段的实现方式。

同一个需求，可以用脚本、成熟组件、平台能力或定制开发解决。选择之前需要同时考虑：预期收益、实施成本、现有基础设施、团队维护能力、依赖关系、故障影响范围及后续扩展空间。

方案记录不应只有架构图和部署步骤，还应说明：

- 解决哪一个具体问题，不解决哪些问题；
- 为什么采用当前方案，考虑过哪些替代方式；
- 关键的资源、配置和依赖边界在哪里；
- 付出了哪些成本，接受了哪些取舍；
- 什么条件发生变化时，需要重新评估设计。

复杂度本身没有价值。如果一种更简单的实现已经能够可靠满足目标，就不必为了“完整”而提前引入所有组件。

**工程设计追求的不是局部最优，而是在可靠性、成本、交付与维护之间取得可解释的平衡。**

## 04 · 把技术实现变成可靠交付

服务能够启动、接口能够返回、测试脚本能够通过，只能说明系统满足了部分条件。真正进入使用场景后，还会面对异常负载、依赖故障、配置变更、版本升级以及交接维护。

因此，交付至少需要回答三类问题：

| 阶段   | 核心问题             | 关注内容                                     |
| ------ | -------------------- | -------------------------------------------- |
| 实施前 | 准备是否充分？       | 需求、环境、依赖、容量、风险、验收标准       |
| 实施中 | 行为是否符合预期？   | 功能测试、资源状态、异常处理、变更控制       |
| 实施后 | 能否持续运行与恢复？ | 运行基线、监控告警、回滚、恢复演练、文档移交 |

性能优化也遵循同样的原则：先有 Baseline，再定位瓶颈，控制关键变量，比较调整前后的吞吐、延迟、错误率、资源开销与业务体验。一个指标变好，但成本、风险或其他指标显著恶化，未必意味着整体方案更优。

验证结论需要明确适用环境和边界。实验结果不能自动等同于生产承诺；问题暂时消失，也不等于根因已经消除。

## 05 · 让风险尽可能早于故障被发现

运维工作不可避免地需要处理异常，但长期价值不应只用处理了多少次故障来衡量。

对于已经知道的风险，更合理的工作是将它前移：在设计时考虑单点与容量，在部署前检查配置和依赖，在交付时验证异常与恢复，在运行中观察趋势，在变更时控制影响范围。

这一过程可以分为三个层次：

- **事前减少发生概率**：配置基线、容量规划、设计评审、设备验收、自动化检查、变更预案。
- **事中限制影响与缩短恢复**：可观测性、分级告警、隔离、限流、灰度、回退与应急流程。
- **事后消除重复诱因**：RCA、风险复盘、规则优化、流程修订、自动化改造和必要的演练。

这里需要区分**看见问题**和**治理问题**。Metrics、Logs、Traces 帮助理解系统状态；合理的告警、处置策略、变更机制和责任分工，才进一步让状态变得可控制、可改善。

预防并不意味着保证系统永远不出故障，而是尽可能让风险提前暴露、故障范围可控、恢复过程可预期，并让同类问题发生得更少。

## 06 · 让一次经验成为可复用的方法

一次故障处理完成后，最容易留下的是几条有效命令；最值得保留的，则是当时如何一步步判断出这些命令适用。

因此，故障与实验记录尽量包含完整上下文：

**场景与环境 → 现象与影响 → 证据与假设 → 处理动作 → 验证结果 → 适用边界 → 后续改进。**

记录之后，还需要再向前走一步：

- 将重复操作整理为 **SOP**，降低执行中的随意性；
- 将异常判定、定位路径和恢复步骤整理为 **Runbook**；
- 将容易遗漏的条件整理为检查清单、配置标准和验收项；
- 将反复出现的人工判断逐步转化为监控规则、自动检查或受控自动化；
- 对尚未证实的根因和推测明确标注，而不是把猜想写成结论。

文档只有在别人能够看懂、复现、验证，并随着环境变化持续修订时，才真正具有复用价值。

经验沉淀的目的不是让知识库越来越厚，而是让相似问题不必一次次从头解决，让日常运行不再过度依赖个别人的记忆和临场经验。

## 07 · 用实际业务结果衡量技术价值

一套系统是否有价值，最终不能只看部署了多少组件、接入了多少设备，或者生成了多少张报表。更重要的是：它是否改善了某个明确的业务场景。

技术方案需要回答的问题包括：谁真正需要它？原来的流程有什么成本？上线后节省了什么、改善了什么？使用者是否愿意持续使用？维护这套能力又需要付出多少代价？

数字可以用于比较，却不能脱离条件独立成立。QPS、可用性、响应时间、人工工时和资源利用率，都需要与具体场景、统计口径和业务目标关联。**没有可靠数据，结论只是感觉；没有业务场景，数字也难以说明价值。**

对于跨部门系统，技术可用只是落地的一部分。清晰的责任边界、合理的使用门槛、培训与反馈机制，往往决定方案能否真正进入日常流程。比单方面推动使用更有效的，是让需求方参与场景定义，在使用过程中持续反馈，再依据真实效果调整系统。

工程不只负责实现功能，还需要关注功能是否被正确使用、是否值得长期维护，以及是否真正解决了最初的问题。

## 08 · 关于这个知识库

这里的内容会持续迭代，既包括基础知识，也包括实验过程、失败尝试、排障记录和工程决策。

不同主题深度不尽相同，但尽量遵循一致的写作原则：

- **讲清上下文**：标注环境、版本、依赖和适用条件。
- **区分事实与判断**：实验观测、机制解释、个人假设与待验证内容分别说明。
- **保留过程与证据**：不只给出最终命令，也记录为什么这样做、如何确认结果。
- **写清失败与边界**：错误尝试、未解决问题和回退条件同样有参考价值。
- **允许持续修订**：随着版本、环境和实践变化，更新结论、流程与标准。

这个仓库不是一份已经完成的标准答案，更像一本持续校验的工程笔记。技术会不断更新，但识别问题、理解机制、审慎决策、验证结果和沉淀经验的方法可以长期复用。
