# Cloud Engineering Notes

一个记录 **Linux、Cloud、DevOps、Kubernetes、Observability 与 AI Infra** 学习和工程实践的开源知识库。

这个项目不以收集知识点和命令为目的，而是记录我如何理解系统、观察系统、分析问题和进行优化，并在实践中逐步形成自己的工程方法。

## 1. 为什么建立这个项目

技术学习很容易停留在“知道是什么、记住怎么用”。

但在真实系统中，问题往往不会直接告诉你答案。面对一次延迟升高、请求超时、连接异常或服务故障，需要回答的是：

* 问题发生在哪一层？
* 数据或请求经过了什么环节？
* 当前系统处于什么状态？
* 哪些指标能够证明问题存在？
* 为什么会出现这个现象？
* 如何验证自己的判断？
* 修改之后是否真正改善？

因此，我希望把学习从**知识记忆**转变为**系统理解和工程实践**。

## 2. 我的学习理念

学习一个技术，不只关注它“是什么”，还关注它在系统中的位置、作用和运行过程。

我会尽可能从以下几个方面理解一个技术：

* **What**：它是什么，解决什么问题？
* **Why**：为什么需要它？
* **How**：它如何工作？
* **Data Flow**：数据、请求或任务如何经过它？
* **State**：系统有哪些运行状态？
* **Observe**：如何观察这些状态？
* **Failure**：什么情况下会出现异常？
* **Troubleshooting**：如何根据证据定位问题？
* **Optimization**：瓶颈在哪里，应该优化什么？
* **Verification**：如何证明优化有效？

这也是我学习 Linux、网络、Nginx、数据库、容器、Kubernetes 以及 AI Infra 时，希望保持的一套统一思维。

## 3. 语言与思维

我认为，**语言不仅是表达工具，也是建立思维模型的工具。**

“服务器很慢”只是一个模糊现象。

当它被进一步描述为：

* HTTP Latency 升高
* Upstream Response Time 增加
* 请求开始堆积
* PHP-FPM Worker 不足
* CPU / I/O / FD / TCP 状态异常

问题才开始变得可以分析和验证。

因此，我希望训练自己从模糊的自然语言逐渐走向精确的工程语言，再从工程语言进一步落实到**状态、指标和证据**。

## 4. 我的观测理论

我认为：

> **理解系统的前提，是能够观察系统。**

一个运行中的系统包含大量状态，而命令、日志、指标、Trace、网络抓包等工具，本质上都是观察系统的不同窗口。

因此学习一个系统时，我会关注：

* 正常状态是什么？
* 异常状态是什么？
* 有哪些关键指标？
* 指标之间有什么关系？
* 从哪里能够观察？
* 一个异常现象可能对应哪些原因？

例如 Linux 中的 CPU、Memory、I/O、Network、Process、File Descriptor、TCP Connection 等资源，都应该放到整体运行状态中理解，而不是孤立学习某一个命令。

所以：

> **命令不是知识本身，命令是观察系统的工具。**

## 5. 我的优化理论

我认为：

> **优化不是盲目调整参数，而是找到并改变真正的系统瓶颈。**

优化之前先建立 Baseline，然后通过压力、流量或实际业务观察系统，定位瓶颈，再修改关键变量并重新验证。

优化关注的也不应该只是单个指标，而应该结合：

* Throughput / QPS
* Latency
* Error Rate
* CPU / Memory
* I/O
* Network
* Connection / Queue
* Goodput
* 稳定性与资源成本

最终判断的是：**系统是否以更低的成本、更高的稳定性完成了更多有效工作。**

## 6. 我的工程方法

我希望逐渐形成一个稳定的工程闭环：

**理论 → 部署 → 建立基线 → 观察 → 制造压力或异常 → 分析 → 假设 → 验证 → 优化 → 再验证 → 总结**

其中最重要的不是记住某个解决方案，而是能够解释：

> **为什么出现这个问题，为什么采取这个动作，以及如何证明这个动作有效。**

一次故障最终应该沉淀为可以复用的工程经验，而不是停留在一次性的解决方案。

## 7. 项目的目的

这个仓库既是我的学习记录，也是我的工程知识库。

我希望通过持续实践，逐渐建立以下能力：

* 理解复杂系统和完整数据流
* 建立系统观测能力
* 根据现象和证据进行故障排查
* 分析系统瓶颈和性能问题
* 通过实验验证技术方案
* 将一次实践沉淀为可复用的方法
* 将不同技术领域放入统一的工程思维中理解

技术和工具会不断变化，但**理解系统、观察系统、定位问题、优化系统和验证结果**的能力具有长期价值。
